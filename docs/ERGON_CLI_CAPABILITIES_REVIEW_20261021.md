# ERGON 제작 결과 확인 계약 — 공식 capabilities 1회 조사

기준: 2026-10-21 KST / 영겁.
코드 기준: `codex/home-gnosis-iris-integration-20261019` / `a6bea6824fcff9c7566834c83a979d9985869b6b`.

## 실행 범위와 보존 확인

- 한설은 capabilities 1회만 승인했다. 캐시 갱신 위험 보고 후 **원본 별도 복사 보존·CLI 자체 캐시 갱신**도 추가 승인했다.
- 원본 응답 캐시를 Git 제외 로컬 영역에 새 복사본으로 보존하고 원본/복사본 SHA256 일치를 확인한 뒤 실행했다. 기존 cache 파일을 이동하거나 삭제하지 않았다.
- 공식 CLI의 인자는 `capabilities` 하나뿐이었다. **실제 실행1회 / exit0 / 유효 JSON / 명령28개 / stderr0바이트**. 재시도0, 다른 게임 명령0.
- CLI 자체 응답 캐시는 승인 범위에서 갱신됐으며 원본 복사본 해시는 유지됐다. 응답 전체/캐시/백업은 Git에 넣지 않는다.
- 점검한 native 보호 기록6개는 실행 전후 파일 목록·크기·바이트 해시가 동일하다. 내용은 해독하지 않았고 원장/설정을 변경하지 않았다.
- 게임/IRIS 실행·종료·재시작, 제작/채집/수령/재고 등 별도 게임 조회, 제품 코드·DB·commit/push·배포0. 본 문서는 익명화한 분석 결과만 새로 작성한다.

## 증거의 정확한 범위

이번 결과는 현재 클라이언트가 **설명하는 명령 계약**이다. 실제 제작 결과·장비 재고·멤버십·시설 데이터를 조회하거나 생성한 것이 아니다. 명령 행에는 Description/OutputExample/Note 등이 있으며, 아래 핵심 반환값은 주로 텍스트로 설명돼 있다. 검증 가능한 보상 항목의 정식 JSON Schema까지 받은 것으로 해석하지 않는다.

## 네 가지 우선 조사 결과

| 항목 | 현재 capabilities에서 확인 | 확인하지 못한 것 | ERGON 판단 |

| 가공 시설 정원·빈자리·작업 ID | 작업은 DisplayName/FacilityName/State/IsCompleted/RemainingSeconds, 시설 완료품 전체 수령. queue_full·insufficient_facility_level 사유 | 총정원·빈자리 수·실제 시설 레벨 값·안정 job/work ID·슬롯 번호/처리 순서 | 기본7·현재 작업 수·실패 메시지로 정원을 만들지 않음. 시설명은 묶음이지 고유 작업 ID가 아님 |

‘확인하지 못함’은 **이번 반환 명령28개의 설명/예시 범위**다. 클라이언트 내부에 데이터가 전혀 없거나 향후 지원도 불가능하다는 선언이 아니다.

### 중요한 오해 방지

1. `execute_crafting.invalid_count`의 `maxCount`는 **시설별 한 제작 요청의 craftCount 상한**이다. 가공 시설 슬롯 정원/빈자리 정보가 아니다. 상한을 알아내려고 잘못된 수량으로 게임 실행을 시도하지 않았다.
2. `ProducedPerCraft`는 기본 예상 계산에 쓸 수 있지만 실제 성공/실패·추가 보상을 대신하지 않는다. 이번 요청의 ‘성공률80%’는 실제 품목에 대해 확인한 수치가 아니다.
3. 제작 완료 응답의 보상 필드 **존재 계약**은 확인됐다. 그 배열의 행 구조, 목표 장비를 식별하는 방법, 대성공 보상과 기본 보상의 합산 방식이 실검증됐다는 뜻은 아니다. 수령의 과거 Name/Amount 형식을 제작 보상에도 임의 적용하지 않는다.
4. 제작 설명은 `stopped_by_user`를 새 생산 없음으로 안내하지만, 기존 IRIS의 보수적 unknown/중단 처리까지 이번 조사만으로 바꾸지 않는다. 중단/부분 처리/비용은 별도 계약 검증 대상이다.
5. 수령은 FacilityName이 같은 시설의 완료품 전체에 영향을 준다. 제작 보상과 시설 수령 보상은 귀속 범위가 다르므로 같은 판정기로 무조건 합치지 않는다.

## 기존 계산의 최소 수정 제안 — 구현 전

### 1. 먼저 예상량의 확정 진척 가산을 차단

`lib/irisErgonCraftGoal.ts`의 `observeErgonCraftGoal`은 completed·metadata·날개가 맞으면 expectedOutput를 completedOutput에 더한다. 다음 원칙으로 바꿀 범위를 승인받는다.

- 예상 산출량: 준비 화면/재료·비용 계획에만 사용.
- 실제 확인 수량: 검증된 품목별 보상 또는 별도 사용자 확인으로만 증가.
- 명령이 completed여도 수량 근거가 없으면 목표는 **결과 확인 필요**. 명령 상태 원문은 보존.
- `DesktopErgonExecution` 표시, `DesktopErgon` 남은 목표, `DesktopErgonQueue`의 remainingPlans/reservedOutputs도 같은 기준으로 바꾼다. 예상 진척이 예약을 오염시키지 않게 한다.

### 2. 공식 보상 증거를 안전하게 전달

대상 후보: `iris/desktop-life-policy.cs`, `desktop-life-executor.cs`, `lib/irisErgonActions.ts`, bridge parser/tests. 새 자동 생산 루프가 아니라 **결과 검증 경계**다.

- 후속 승인 아래 보상 배열의 실제 형식·의미를 먼저 확보한다. capabilities는 정확한 row schema를 주지 않았으므로 필드 이름을 지어내지 않는다.
- 요청ID·목표/캐릭터 범위·품목과 연결해 기본 보상/criticalRewards를 분리 검증한다. 목표 품목과 정확히 대응한 확인 수량만 한 번 반영한다.
- 레시피 이름과 결과물 이름/등급이 다를 수 있다. 부분 문자열·등급 접미사 제거로 목표 품목을 추정하지 않는다.
- 보상 누락/모순/잘못된 수량/미지원 형식은 null/확인 필요. 공식 의미를 확인하기 전 빈 배열을 성공0개 또는 예상량 확보로 간주하지 않는다.
- bridge는 새 증거 버전의 하위 호환을 설계한다. 구버전·과거 예상량/완료 원장을 실수량으로 소급 승격하지 않는다. 예상 metadata와 원본 보호 기록은 변경하지 않는다.

### 3. 장비 사용자 확인은 별도 출처

보상으로 실제 목표 품목 수량을 확정할 수 있으면 그 증거를 우선 검토할 수 있다. 그러나 일반 장비 전체 보유량 조회가 없으므로 ‘현재 가방에 계속 보유 중’까지 자동 보증하지 않는다. 외부 소비/이동·재시작·응답 유실은 별도 대조가 필요하다.

공식 수량 증거를 얻지 못하면 ‘이번 추가 확보량’을 사용자에게 확인받고 출처/시점/목표/요청과 연결한다. ‘현재 총보유량’ 방식은 시작 수량과 외부 이동을 확인할 수 있을 때만 사용한다. 중복·정정 이력을 보존하고 기계 검증과 사용자 확인을 구분한다. 사용자 확인으로 과거 unknown 원장을 성공으로 바꾸거나 추가 소비 차단을 해제하지 않는다.

### 4. 상태와 계속/보류/그만하기

- **목표 달성:** 신뢰 가능한 확인 수량이 목표 이상. 출처 표시, 추가 생산 없음. 미해결 실행 보호 상태는 별도로 유지한다.
- **목표 미달:** 확인된 수량이 부족. 계속하기는 최신 재고/예약/진행 작업을 대조해 부족분을 다시 계획할 뿐 즉시 재소비하지 않는다. 새 예산은 재승인한다.
- **결과 확인 필요:** 수량 불명·충돌·미해결 실행. 부족 수량을 확정하지 않고 추가 소비를 막는다.
- **보류:** 목표·확정 진척·증거·보호 기록 보존.
- **그만하기:** 활성 목표 취소/목록 제거. 이미 진행 중인 게임 행동 취소와 동일시하지 않으며 감사/unknown 원장은 보존.

## 후속 회귀 검증 제안

1. completed·craftCount4·기본산출1·보상 미확인 → 확정4/목표 달성 금지.
2. 공식적으로 검증된 목표 보상3개/목표4 → 진척3·남은1. 명령 횟수4와 분리.
3. 기본 보상/대성공/비목표 보상·품목명 변형·중복 응답·늦은 응답·다른 캐릭터를 구분.
4. 배열 누락/미지원 형식/음수·소수·범위 초과·모순은 확인 필요. 실제0과 null을 구분.
5. 실제 수량이 없는 기존 completed 원장을 재생해도 새 확정 진척이 생기지 않음.
6. UI 남은 목표·완료품 예약·사용자 확인 중복/정정·재시작 보존이 동일 기준을 사용.
7. nonce/lease/비용/컨텍스트·원본 unknown·목표 삭제 후 기록 보존을 그대로 검증.

이번에는 회귀 테스트나 제품 수정을 추가하지 않았다. 현재 Node111/native 합성 통과 기록은 과거 조사 결과이며, 위 새 수량 계약의 통과 결과가 아니다.

## 다음 승인 전 남은 사항

가장 먼저 승인받을 구현 후보는 **예상 진척 가산 차단 + 수량 확인 필요 표시/계산**이다. 보상 파서는 실제 row 계약과 의미를 확보한 다음 별도로 설계한다. 보상 형식 확인을 위한 기존 응답 열람 또는 새 소량 게임 시험은 이번 capabilities 승인에 포함되지 않는다. 장비 사용자 확인 기록의 저장/정정 방식도 검토 뒤 구현한다.

명령 목록을 얻었다는 이유로 제작·재고 조회·시설 슬롯 탐색·멤버십 조회를 추가 실행하지 않는다. 코드·DB·main·Production·공개 IRIS 잠금·push/배포는 모두 그대로다.
