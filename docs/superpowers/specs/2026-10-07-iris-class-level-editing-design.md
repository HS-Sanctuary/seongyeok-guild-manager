# IRIS 클래스 레벨 직접 수정 설계

상태: 2026-10-07 사용자 설계 승인(“설계대로 진행해줘”). 구현 계획 검토 후 현재 폴더에서 직접 실행한다. 운영 쓰기·commit/push 승인으로 확대하지 않는다.

## 의도와 확정된 사용 방식

- 한설이 게임을 보면서 직접 적는다. 기본값은 선택한 본인 캐릭터의 현재 생텀 DB `levels`다.
- 클래스별 레벨 입력을 제공하고 닉네임 재확인 창은 띄우지 않는다. 캐릭터 선택을 대상 지정으로 사용한다.
- 마지막 유효 수정 후15초 자동저장, 기존 지금 저장/변경 버리기/저장 확인 시각을 함께 적용한다.
- 캐릭터를 떠나면 이전 캐릭터 변경의 대기 시간을15초로 재설정하고 별도로 보관한다. 계정 전환 시 다른 계정 큐를 전송하지 않는다.
- 게임 전체 클래스 조회, 스탯 저장, 시낙시스, 자동 게임 작업, 운영 DB 구조/RLS/권한 변경은 범위 밖이다.

## 조사로 확인한 기존 경계

- `components/iris/DesktopCheckboard.tsx` 클래스 영역은 조회 전용이며 `lib/irisKronos.ts`가 활성 카탈로그 ID/이름 및 저장 레벨을 만든다.
- `characters.levels`는 문서상JSONB이며 클래스 이름별 수치 객체를 사용한다. 새 테이블이나 컬럼은 필요 없다.
- `irisDesktopQueue.ts`/`desktop-store.cs`는 schema1을 엄격 검증하며 현재 일일/주간/어비스/레이드와 기간 키만 허용한다. 클래스는 초기화 기간이 없고 미등록 값이 가능하므로 숙제 숫자0으로 위장하지 않는다.
- controller가 하나의 직렬 전송/보호 보관/종료 절차를 소유한다. 별도 클래스 타이머나 폴링·저장 엔진을 만들지 않는다.

## 접근 비교와 선택

1. 화면에서 클래스만 바로 저장: 빠르지만 기존15초 보관/종료/재실행 보장과 분리되므로 제외.
2. 클래스를 주간 숙제로 위장: 기간 초기화/상한/미등록 의미가 달라 제외.
3. 기존 큐를 숙제/클래스의 명시적 종류로 확장: 변경 범위는 넓지만 사용자가 요청한 동일 저장·복구 동작을 유지할 수 있어 권장한다.

## 화면과 입력

- 현재 클래스 아코디언을 유지하고 각 행을 클래스 이름+작은 레벨 입력으로 구성한다. 현재 DB값 또는 미등록을 기본 표시한다.
- 미등록은 빈 입력으로 표시한다. 빈값/소수/음수/범위 밖은 오류 안내를 표시하고0이나1로 자동 변환하지 않는다. 유효한 정수1~1000만 대기함에 넣는다(현재 조회 계약 범위). 저장값 삭제 기능은 이번 범위에 넣지 않는다.
- 숫자를 지우고 다시 입력하는 중간 상태는 입력용 초안으로 관리한다. 유효하지 않은 초안이 있는 선택 캐릭터의 저장은 막고, 다른 캐릭터의 유효 대기 항목은 영향을 받지 않는다. 이전 유효 대기값이 입력 오류 뒤 몰래 전송되지 않도록 해당 편집을 보류한다.
- 유효한 값을 변경할 때만15초를 갱신한다. 원래값으로 되돌리면 대기 변경을 제거하고 요청을 보내지 않는다.
- 캐릭터 변경 전 유효하지 않은 입력은 명시 안내하고 해당 입력 정정/되돌리기 후 이동한다. 단순 캐릭터 전환마다 확인 모달을 띄우지 않는다.
- 저장 중 추가 수정/포커스/커서·접힘·스크롤을 보존한다. 기존 긴 닉네임/6테마/rem/320폭 기준을 유지한다.

## 서버 저장 계약

- 클래스 전용 같은 원본POST API를 추가하고 기존 서버 세션으로 본인 소유 `characterId`를 검증한다. 입력에 owner/클래스 이름/levels 전체 객체/다른 필드 수정 권한을 받지 않는다.
- 요청은 requestId,accountId,characterId,classId,baseLevel(정수 또는 실제 미등록null),desiredLevel만 엄격 허용한다. 클래스 ID→이름은 서버의 활성 카탈로그로 해석한다.
- 신뢰할 수 없는 현재DB값은0/null로 정규화해 덮어쓰지 않는다. 기존 levels가null/정상 객체일 때만 지원하고, 선택 클래스가 비정상 수치/타입이면 수정 거절 및 웹 관리 안내로 보존한다. 화면 조회에서 미등록과 잘못된 원본을 구분할 최소 쓰기 문맥도 제공한다.
- 현재 선택 클래스 값이 baseLevel과 다르면 충돌, desiredLevel과 같으면 변경 없이 성공을 확인한다.
- 최신 levels 객체를 읽고 변경한 클래스 키만 합친다. 비활성/알 수 없는 다른 키를 삭제하지 않는다.
- UPDATE는 id+owner+읽은 levels 원본 전체를 조건으로 비교(CAS)한다. null은IS NULL,JSONB는 기존 숙제와 같은 원본 직렬화 조건을 사용한다.0행이면409, 재시도 덮어쓰기 없음. 다른 필드·다른 클래스 보존을 테스트한다.
- API는 출처/JSON형식/스트림 크기 제한과401/403/409/503,응답 requestId 및 저장값 일치 검증을 갖춘다. 서비스키는 기존 서버 경계 안에 둔다.
- 이번 범위는 웹의 모든 기존 쓰기 경로를 바꾸는 것이 아니다. 웹의 오래된 전체 객체 저장이 이후 덮어쓸 가능성은 별도 위험으로 기록하고 동시 수정 합성/사용자 검증에서 확인한다.

## 통합 큐와 보호 저장 버전

- schema2는 task/class를 판별하는 union을 사용한다. task는 기존 기간 키·횟수, class는 클래스ID·미등록null/정수 기준값·유효 목표레벨을 엄격 검증한다. 단일 inflight/계정·캐릭터·환경 격리/500항목·크기 제한을 유지한다.
- 같은 캐릭터의 마지막 유효 조작은 숙제/클래스 양쪽 대기 시간을 함께15초로 갱신한다. 지금 저장/버리기도 선택 캐릭터의 두 종류에 모두 적용한다. 계정 전체 요약과 선택 캐릭터 버튼 범위를 명확히 안내한다.
- 클래스에는 일/주간 period 만료를 적용하지 않는다. 숙제에는 기존06시/월요일 정책을 그대로 적용한다.
- 성공 시 선택 클래스 baseline/화면 및 마지막 저장 확인 시각을 갱신한다. 늦은 A응답으로B화면을 바꾸지 않는다. 불명 결과는 자동 재전송하지 않고 실제 값 조회 후 명시 확인/재시도 흐름을 유지한다.
- schema1은 기존 그대로 검증하고 schema2로 명시 변환한다. 복원된 pending/inflight는unknown 보류, 사용자·소유권·기준값 재확인 뒤에만 저장한다. schema2를 schema1로 덮어쓰지 않는다.
- 새 DPAPI 파일/entropy 버전을 사용하고 기존 암호문을 보존한다. 동일 공유 실행 잠금 안에서 기존v1을 읽어 검증→v2 원자 저장/재확인→v1을 복구용 이름으로 이동하는 순서다. 실패는 편집·전송을 잠그며 원본 보존. v1/v2가 동시에 활성 경로에 남는 불명확 상태는 자동 전송하지 않는다.
- 구버전 native와 신버전 UI 조합은 schema2 보관 실패로 잠그고 앱 재실행 안내한다. 전용 프로필/로그인/공유 mutex/출처·epoch 브리지는 약화하지 않는다.
- 이전 앱으로 즉시 되돌리면 최신v2를 읽지 못하므로 미저장 데이터의 v1 자동 역변환이나 구버전 실행을 유도하지 않는다. 문제 시 신규 편집을 막고v2 보관/복구 안내를 제공한다.

## 변경할 영역

- 클래스 입력/표시: DesktopCheckboard,DesktopCenter,page,저장 요약과 CSS.
- 전송/저장: irisDesktopTransport,irisDesktopController,irisDesktopQueue/Presentation,클래스 API와 서버·순수 검증 모듈.
- 보호 보관: irisDesktopStore,desktop-store.cs 및 필요한 bridge 크기/schema 경계,버전 전환 회귀.
- 구조/인계/피드백 문서. 기존 무관한 공지 초안·루트 파일 삭제·테마 검증 파일은 건드리지 않는다.

## 검증 및 완료 기준

- 테스트를 먼저 실패시키고 구현한다. 미등록/현재값/감소/원복0쓰기/잘못된 숫자·타인·비활성 클래스·카탈로그 오류·크기 제한을 검증한다.
- 다른 클래스 보존·CAS0행·경쟁 수정·중복 응답·401·응답 유실·부분 성공·새 수정/선택 전환/계정 격리·숙제06시 vs클래스 무초기화를 검증한다.
- v1→v2 원자 보관·중간 실패/손상/잘못된 schema·재실행 보류·종료 및 단일 실행을 Windows 합성 자료로 검증한다. 실제 보호 대기함/쿠키/비밀값을 읽거나 추출하지 않는다.
- 전체Node/별도타입/분리빌드·합성 브라우저 숫자입력/포커스/72레이아웃을 확인한다. 기존 브라우저 로그인 선택자 timeout은 정확한 원인 확인 후 fixture를 보완하고 통과를 다시 확인해야 한다.
- 실제DB 쓰기는 한설이 본인 캐릭터에서 레벨1개 변경→15초→웹 비교,지금 저장,캐릭터 변경 보관을 직접 확인한다. 자동 테스트 성공과 구분한다.
- 완료 보고에는 운영 미배포/미푸시와 사용자 확인 대기를 명시한다. 이번 설계 작성 자체로 제품 코드/DB는 변경하지 않는다.

## 설계 자체 점검

- 숙제 기간과 영구 클래스,미등록과0,계정/캐릭터,저장 확인 시각과 실제DB시각을 분리했다.
- 모든 저장 경로는 기존 단일controller를 거치고 구버전 대기함은 무손실 보존/실패잠금으로 처리한다.
- 공식게임조회/운영구조변경/신원추정/무관한화면개편은 추가하지 않았다.
