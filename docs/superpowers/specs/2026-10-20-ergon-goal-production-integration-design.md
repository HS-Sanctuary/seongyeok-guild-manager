# CHRONOS ↔ ERGON 목표 생산·재개·시간 예측 통합 설계

기준: 2026-10-20 KST / 영겁 / 코드 기준 `5102571c65621d971609389110cd1bf2963f843f`와 이번 로컬 표시명 수정.
상태: **사용자 요구를 반영한 설계 초안. 새 자동 실행 코드·DB·원격 기능은 구현하지 않음.**
이번 표시명 수정은 별도 최소 변경이며 ERGON 자동 생산 완성을 뜻하지 않는다. 구현 명세·실행계획·소비 정책은 후속 검토 대상이다.

## 1. 제품 경계와 명칭

- 공식 사용자 표기는 영문 **CHRONOS**, 한글 **크로노스**. 캐릭터 관리·숙제·물물교환·상점·임무게시판의 기존 역할을 유지한다.
- `/character`, 기존 API·DB·RLS·localStorage·native 저장 구조, `kronos` 계열 함수/파일/타입/프로토콜은 변경하지 않는다. 화면 표기를 내부 식별자 마이그레이션으로 확대하지 않는다.
- ERGON은 생산 실행을, CHRONOS는 필요 물품과 기존 캐릭터/체크 상태를 담당한다. 생산 성공만으로 교환·임무 제출·숙제 완료 체크를 자동 처리하지 않는다. SYNAXIS의 기존 완료 동기화도 그대로다.
- 현재 공개 ERGON 잠금은 유지한다. 낚시·원격 작업·무한 반복은 이번 구현 범위가 아니다.

## 2. 사용자 입력의 의미 — 추가 생산과 부족분

| 진입점 | 예시 | ERGON 목표의 의미 |
| --- | --- | --- |
| ERGON 직접 요청 | 현재 목재30개, “추가100개 만들기” | 시작 가방 기준+100개, 기준 보유 목표130개 |
| CHRONOS 부족분 만들기 | 제출에 목재100개 필요, 사용 가능한 미예약 재고30개 | 부족70개를 추가 생산, 같은 재고 조건에서 기준 보유 목표100개 |

CHRONOS 물물교환·임무게시판에 필요한 품목·수량이 확인된 경우에만 미래 `부족분 만들기` 진입점을 제공한다. **이번에는 버튼이나 handler를 추가하지 않는다.** 대상 후보는 `components/character/TradeList.tsx`, `KronosWorkspace.tsx` 및 IRIS의 기존 교환/임무 표시 경로이며, 실제 품목 요구량의 구조화 여부는 구현 전 확인한다.

진입 정보에는 선택 계정/캐릭터 범위, 원래 요구의 참조, 원문 품목 식별, 필요량, 재고 관측 시각을 연결한다. 서버 요청의 필요량이나 화면에 남은 재고를 신뢰해 즉시 소비하지 않는다. ERGON이 실제 가방·미예약 재료·해금·도구·무게·날개를 다시 확인하고 시작 미리보기를 만든다.

- 두 진입점 모두 미수령 가공 산출을 사용 가능한 재료로 합산하지 않는다.
- 같은 원재료를 여러 목표에서 이중 예약하지 않는다. 기존 `irisErgonSupply.ts`의 공유 재료·완료 목표 예약을 재사용한다.
- 창고 재료는 전송기 설치·부스러기 비용·게임 주간 확인창 조건을 별도로 표시한다. 확인되지 않은 창고 재고를 무료 가방 재고로 합산하지 않는다.
- 부족분이0이면 생산 명령을 보내지 않는다. 필요량/레시피/캐릭터/사용 가능 재고가 바뀌면 계획과 승인 범위를 재검토한다.

## 3. 시작과 목표형 생산

`실재고 확인 → 부족분·재료 경로 계산 → 시작 승인 → 채집 → 가공 등록 → 완료 대기 → 수령 확인 → 후속 제작 → 목표 확인`

사용자는 **실행시간이나 예약 시각을 지정할 필요가 없다.** 사전 조건이 확인된 작업은 시작 승인 후 즉시 실행한다. 실행을 임의의 시간표에 맞춰 지연하지 않는다. 안전용 명령 timeout·무진척 감시와 “몇 분 동안 실행” 사용자 입력은 다르다.

1. 목표 품목·추가량·필요 재료·기본 초과 산출·확인된 비용을 미리 제시한다. 산출3개/목표100개라면34회·기본102개이며, 등록분170날개는 채집/원격 비용까지 포함한 총액이 아니다.
2. 한 번에 한 소비 명령만 보낸다. 최신 상태와 남은 승인 예산을 매 명령 전에 검사하고 기존 native executor/원장 선기록을 사용한다.
3. 부족 재료만 채집한 뒤 가공한다. 첫 완성 사례도 **목재 추가100개를 부족 통나무 채집부터 처리**하는 end-to-end 흐름이며, 단일 등록만 완료해 요구를 충족했다고 보고하지 않는다.
4. 시설이 가득 차면 현재 작업의 완료를 관측하고 수령 후 빈자리에 필요한 만큼 재등록한다. 기본7칸·현재 작업 수를 실제 정원으로 단정하지 않는다. 정원/여유를 확인할 수 없으면 자동 추가 등록을 차단한다.
5. registered는 등록 성공, 작업의 completed는 가공 완료, collected는 수령 결과다. 이 상태들을 목표 완료로 합치지 않는다. 작업행 감소와 보상/재고를 대조하고 타 앱·수동 작업이 섞여 귀속이 불명확하면 멈춘다.
6. 수령은 시설 전체 완료품에 영향을 준다. 승인 시 그 범위를 보여주고, 다른 품목을 받은 양을 목표 품목의 진척으로 세지 않는다.

명령마다 확인하는 현재 구현을 “목표 범위 한 번 승인”으로 바꾸는 것은 후속 소비 정책 변경이다. 목표·최대 등록 횟수·확인된 소모 상한·시설 전체 수령 범위와 승인 철회/추가 확인 조건을 명세화해야 한다. **사용자 지정 실행시간을 필수 승인 항목으로 요구하지 않는다.** 기존 제작 목표의5분 준비 기한은 현재 코드의 사실이며 새 전체 생산의 사용자 실행시간 설정으로 가져오지 않는다.

결과 불명·비용 불명·외부 개입·새 확인창에서는 추가 소비를 자동으로 진행하지 않는다. 게임 확인창 자동 승인, 중복 재전송, 과거 unknown 성공 주입은 금지한다.

## 4. 가공 시간 예측 — 아는 구간만 표시

기존 `get_altering_works` 정규화는 시설·품목·완료 상태·remainingSeconds를 제공한다. 관측 시각과 함께 사용하되, 안정적 작업 ID·총정원·시설 병렬 처리량·새 작업의 표준 소요 시간은 현재 모델에 없다.

- 현재 관측된 미완료 작업의 `관측 시각 + remainingSeconds`를 해당 작업의 **게임 표시 기준 예상 완료**로 제시한다. 화면 카운트다운은 로컬 시계로 갱신한다.
- 시설의 다음 수령 후보는 유효한 잔여 시간의 최솟값, 현재 관측된 작업 전체의 마지막 예상은 최댓값으로 계산할 수 있다. 이 값은 **현재 관측된 작업 범위**이며 새로 등록할 물량까지 포함한 전체 목표 ETA가 아니다.
- 시간 값 누락·stale·작업 변화가 있으면 다시 조회하고 “확인 중/갱신 필요”로 바꾼다. 조회 실패를 남은0초·완료로 처리하지 않는다.
- 채집·이동·제작·미등록 가공의 시간은 공식 근거가 없으면 “시간 미확인”이다. 현재 대기열 시간에 임의 초당 생산율을 붙여 정확한 전체 완료 시각을 꾸미지 않는다.
- 향후 품목별 가공 시간은 출처·게임 버전·관측 표본·대기/실행 구간을 구분해 로컬에 축적하는 방식을 검토한다. 공식 지속시간이 확인되기 전에는 참고 범위이며 단일 평균을 보장값으로 쓰지 않는다.

예시 표시: `목재 가공 중 · 현재 등록분 다음 완료 약3분 · 남은 채집/추가 등록 시간 미확인`. 전체 ETA 대신 확인 가능한 현재 단계와 남은 목표를 우선한다.

## 5. 중단 후 재개·보호 기록

상세 목표·단계·승인 범위·확인된 진척·미수령 관측·보낸 요청 ID·결과 상태는 **PC 로컬**을 우선한다. 현재 계획 저장/DPAPI 원장/실행 lease를 재사용하고, 새 체크포인트가 필요하면 별도 버전과 원본 보존·원자 저장·실패 표시를 설계한다. 기존 키/파일을 덮어쓰는 마이그레이션은 이번에 하지 않는다.

- 사용자 중지: 새 소비 요청을 중단한다. 이미 보낸 요청의 실행 종료·결과를 계속 관측한다. CLI 응답 프로세스 종료가 게임 작업 취소라고 간주하지 않는다.
- 앱 종료/충돌: 현재 inflight의 원본을 보존하고 unknown으로 처리한다. “다시 시작”을 눌렀다고 과거 명령을 다시 보내지 않는다.
- 재개: 계정/선택 캐릭터·실제 게임 상태·실재고·가공 현황·최신 비용·남은 목표/예산을 다시 확인한다. 이미 등록·완료·수령된 양을 중복 실행하지 않는다.
- 사용자가 생산물을 소비/이동했거나 다른 앱이 같은 품목을 등록한 경우, 시작 보유 목표를 조용히 늘리거나 그 생산을 내 성과로 세지 않는다. 귀속이 불명확하면 일시정지/재확인한다.
- 확정된 미완료 목표와 진척은 남기되 비용/결과 미확인 상태에서는 추가 소비를 차단한다. 기존 수령용 감사 분리를 모든 생산의 성공·자동 재개 권한으로 확대하지 않는다.
- PC가 꺼지거나 게임 연결이 끊기면 로컬 엔진은 계속 생산할 수 없다. 예약 실행·PC 깨우기·서버에서 게임 명령 대행은 이번 설계의 보장 기능이 아니다.

낚시는 종료·수량·중지 소유권·도구 계약을 별도 검증한다. 현재 통나무 채집 지원을 낚시 또는 모든 채집 품목 지원으로 확대하지 않는다.

## 6. 무료 운영 — 현재 로컬 기본안

**무료 운영이 최우선 제약이다.** 이번 표시명 수정의 신규 네트워크/DB 쓰기/Realtime/Storage/함수 호출은0이다. 향후 ERGON 상세 진행·원장·시설 카운트다운은 PC에 보존하고 기존 로컬 조회를 사용한다. 매초/매15초 게임 진행을 Supabase에 업로드하지 않는다. 서버리스 함수가 가공 완료를 기다리며 실행되는 구조도 채택하지 않는다.

| PC 8시간/일,60초마다 원격 요청 확인 | 288,000회 | 576,000회 | 빈 조회도 누적됨. 전부 함수 경유면 그 호출도 추가되므로 기본안으로 권하지 않음 |
| 같은 조건300초 간격 확인 | 57,600회 | 115,200회 | 원격 기능이 필요할 때만 켜는 후보. 그만큼 수신 지연이 생기므로 로컬 즉시 시작과 구분 |

40명/8시간/30일에15초마다 상세 상태를 서버에 쓰면 **월2,304,000회**다. 변경당 구독자1명에게 메시지1개만 나가도 Realtime200만을 넘고, 두 기기·여러 구독자는 더 늘어난다. 같은 polling을 함수 경유로 하면 함수 호출100만도 넘는다. **현재 로컬15초 조회와 서버15초 쓰기는 전혀 다르다.**

60초 polling576,000회에서 응답 payload만1KB라 해도 약0.576GB이며 헤더/인증·재조회·웹 조회는 별도다. 요청/결과 전체를 전파하거나 상세 로그를 보내면 더 커진다. 40명×기기2대=80연결은 단순 예시일 뿐 기존 SANCTUM 연결·구독 fan-out·다른 조직 사용량과 합쳐 확인해야 한다.

미래 원격 기본 후보는 명시적으로 열린 원격 세션에서만 소유자 범위의 최소 요청을 확인하고, 화면 복귀/사용자 새로고침·적응형 backoff를 우선하는 방식이다. Realtime은 필요가 입증될 때만 선택하며 세부 진행 broadcast는 제외한다. 무기한 대기 polling·상시 서버리스 워커·초당 DB 쓰기·로그 파일 Storage 적재는 무료 대안이 아니다.

## 7. 향후 원격 요청의 보안 경계

모바일은 목표 요청/결과 확인, PC native는 실제 게임 실행과 승인·예산 집행을 담당하는 분리를 고려한다. PC가 연결되고 해당 계정/기기로 허용된 경우에만 실행하며, 모바일 요청이 곧바로 임의 CLI 문자열 실행 권한이 되지 않는다.

기기 허용/철회·계정 소유권·요청 만료·중복 방지 ID·PC 단일 claim·진행 범위·결과 최소화·요청 취소를 설계해야 한다. **이런 테이블·RLS·API가 현재 구현됐다고 기록하지 않는다.** 기존 인증이 Supabase RLS 소유권과 어떻게 연결되는지 확인하고 별도 승인 후 설계한다. 키 추출·직접 게임 접속·유료 서비스 도입은 금지한다.

## 8. 검증/결정/개발 순서

1. 이번 완료 범위: 표시 문구4곳의 최소 변경, 경로/내부 선택값 유지와 비소비성 회귀, 본 설계 및 뉴월 인계 갱신. 공개/원격 반영 없음.
2. 다음 설계 과제: 첫 end-to-end 품목의 정확 재료표·가공 정원/귀속·등록/수령 비용, 목표·예산 승인과 중단/재개 정책 확정. 사용자가 실행시간을 고르지 않는 흐름을 유지한다.
3. 실행 관리자 구현 전: 상태 전이/원장 체크포인트/회복·부족분 예약/ETA 범위를 테스트 계획으로 만든다. unknown·동명/타 앱·재개 때 수동 소비·부분 수령·비용 변동을 우선 시험한다.
4. 합성/native/React 검증 후 별도 직전 승인을 받은 소량 실게임으로 확인한다. 이후 목재 추가100개 전체 목표 검증. 낚시·다중 원격·전체 품목 지원·공개 잠금 해제는 각각 별도 검증/승인이다.
5. 무료 원격 검토는 기존 사용량을 확인할 수 있는 권한과 별도 데이터/배포 승인 뒤 진행한다. 무료 잔여·Hobby 이용 조건이 불확실하면 원격만 보류하고 PC 자동 생산 개발을 계속할 수 있다.

구조상 제안은 기존 native executor·보호 원장을 유지하는 로컬 목표 관리자다. 외부 앱 코드 이식·서버 생산 엔진·기존 저장 키 변경은 하지 않는다. 문서 외 신규 자동 실행 코드는 이번 승인 범위가 아니다.
