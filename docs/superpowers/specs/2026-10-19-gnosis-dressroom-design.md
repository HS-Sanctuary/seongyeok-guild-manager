# GNOSIS 패션 드레스룸 — 1단계 설계

- 작성: 순월 / 2026-10-19 KST
- 상태: 작성 설계 검토 대기. 제품 코드 구현·DB 변경·push·배포 없음.
- 승인된 의도: 실제 마비노기 모바일 외형과 의상을 미리 꾸미고, 그노시스에서 코디·염색 추천 지식으로 공유한다.
- 이번 안전 경계: 별도 브랜치와 폴더, 기존 IRIS·개인 파일 보존, 집 작업 수신 전 운영 DB/main 병합/배포 금지.

## 1. 목적과 성공 기준

길드원은 드레스룸에서 의상 조합과 파트별 색상을 정하고, 완성한 코디를 설명과 함께 그노시스 글에 붙일 수 있어야 한다. 독자는 같은 코디를 다시 열어 자신의 조합으로 바꿀 수 있어야 한다.

전체 목표와 첫 구현을 분리한다. 첫 구현은 브라우저 내부 코디 편집·로컬 보관·코디 파일 내보내기/가져오기 및 작성 초안 연결이다. 다른 길드원에게 영구 공유하는 서버 저장은 실제 그노시스 권한/데이터 계약을 별도 확인한 뒤 진행한다. 브라우저 저장을 길드 공유 완료로 표시하지 않는다.

실제 게임 모델 적용은 출처와 사용 범위가 확인된 호환 자료 확보가 선행 조건이다. 에린넷 파일 주소가 관측되었다는 사실만으로 재사용 승인을 얻었다고 간주하지 않는다. 모델이 없으면 '게임 모델 연결 준비 중' 상태를 표시하며, 임의 인형이나 예시 의상을 실제 게임 외형으로 표시하지 않는다.

## 2. 기존 상태

- app/gnosis/write/page.tsx: 패션 시뮬레이터 적용 옵션, 스크린샷→/api/analyze-item→itemName/rarity/dyeParts 추출 구조가 있다.
- 분석 실패 시 고정 예시 의상을 주입한다. 신규 드레스룸 경로는 이 동작을 재사용하지 않으며, 기존 AI 기능 정비는 별도 변경으로 구분한다.
- 목록/글 작성/상세는 gnosis_mock_db 로컬 저장을 사용한다. 작성자 표시도 시제품 고정값이다. 실제 다중 사용자 게시 기능으로 간주할 수 없다.
- docs/SUPABASE_SCHEMA.md에는 gnosis_guides와 item_data가 기록되어 있으나, 이번 단계에서 컬럼·RLS·쓰기 API를 새로 가정하거나 변경하지 않는다.
- 현재 package.json에 3D 엔진은 없다. 추후 three 패키지와 필요한 타입을 잠금 파일과 함께 고정한다. 제품 의존성 추가는 작성 설계·구현 계획 검토 이후다.

## 3. 선택한 구성과 대안

권장안은 전용 /gnosis/dressroom 화면과 재사용 가능한 클라이언트 뷰어를 두고 작성 초안에 연결하는 구성이다. 회전·색상 변경은 브라우저에서 처리하고 DB 요청을 발생시키지 않는다. 목록은 정적 미리보기로 표시하고 사용자가 입어보기를 선택했을 때만 3D를 로드하는 것을 최종 공유 목표로 한다.

작성 화면에 전체 3D 편집기를 직접 삽입하면 초기 JS와 화면 복잡도가 커진다. 외부 드레스룸 링크만 연결하면 코디 데이터와 그노시스 글을 일관되게 관리하기 어렵다. 따라서 전용 화면과 작은 코디 카드 연결을 선택한다.

## 4. 1단계 화면 및 데이터 흐름

1. 그노시스 작성의 기존 패션 영역에서 드레스룸을 연다. 작성 중 제목·본문·카테고리는 임시 초안으로 보존한다.
2. 부위 목록(모자/상의/하의/장갑/신발/로브/장식), 의상 검색, 선택된 의상 정보, 파트별 색상을 제공한다. 지원하지 않는 부위는 자료 없음으로 표시한다.
3. 뷰어는 회전·확대·시점 초기화를 제공한다. GLB/카탈로그/염색 매핑이 모두 검증된 항목만 실제 착용 가능으로 표시한다.
4. 사용자가 명시적으로 로컬 저장하거나 코디 JSON을 내보낸다. 파일에는 코디 설정만 들어가고 모델·원본 스크린샷·계정 정보는 넣지 않는다.
5. '이 코디로 글 작성'은 같은 브라우저의 초안에 코디를 붙인다. '로컬 초안'임을 표시하고 운영 공유 완료 알림을 사용하지 않는다.
6. 최종 서버 공유 단계에서는 작성자 인증/소유권/길드원 읽기/검증된 코디 스키마를 서버가 확인한다. 이번 단계에서는 실행하지 않는다.

코디 문서 v1: schemaVersion, catalogVersion, title(최대80자), appearance(지원하는 bodyId), equipment(고정 slot→catalog itemId), dyes(itemId와 명명된 partId→#RRGGBB). 최대32KiB, 알려진 부위/의상/파트만 허용한다. JSON에는 파일 URL을 받지 않는다. 가져온 코디는 파싱·크기·버전·ID·색상 검사 후 채택하고, 오류 시 현재 편집 상태를 보존한다.

로컬 보관 키는 sanctum:gnosis:dressroom:v1이다. 계정 정보가 없는 첫 시험은 기기 보관임을 명시하고 민감 정보는 저장하지 않는다. 향후 계정별 보관을 연결할 때는 기존 프로젝트의 확인된 세션 경계를 따른다. 기존 gnosis_mock_db 형식은 삭제하거나 일괄 변환하지 않는다.

## 5. 3D 자료와 렌더링

- 공개 관측에서 GLB 형식과 JSON 카탈로그 분리가 확인됐다. 구체적인 스켈레톤·염색 셰이더·몸 가림 규칙·아이템 전체 목록의 의미는 아직 확인되지 않았다.
- 우리 카탈로그는 id/name/slot/modelPath/compatibleBodyIds/dyeParts/source 정보를 명시한다. modelPath는 관리되는 로컬 정적 경로로 제한하고 사용자 임의 원격 URL을 해석하지 않는다.
- 자료의 호환성을 확인하지 못한 모델은 자동 착용하지 않는다. 바디·리그·의상마다 원점/단위/스켈레톤/가림 구역을 검증한 후 연결한다.
- 최초 실제 자료 검증은 바디1개와 의상1~3개에 한정한다. 자료가 없으면 코디 편집 틀의 검증과 실제 착용 성공을 별도 상태로 기록한다.
- GLB 로드는 선택 항목만, 취소/요청세대 검사로 오래된 로드 결과를 폐기한다. 재선택 시 캐시를 재사용하고 라우트 이탈 시 geometry/material/texture/renderer 및 이벤트를 정리한다.
- 탭 숨김/화면 밖에서는 연속 렌더링을 멈추고 장치 픽셀비는 최대1.5로 시작한다. 자동회전은 기본 끔. WebGL 불가 시 의상·색상 정보는 계속 조작 가능하고 명확한 안내를 보여준다.
- 초기 파일 전송 목표는 모델 포함20MB 이하, 한 의상 추가 로드 목표는5MB 이하로 잡되 실제 자료 측정 전 달성으로 기록하지 않는다.

## 6. 컴포넌트 경계 및 예상 변경 범위

신규: app/gnosis/dressroom/page.tsx, app/gnosis/dressroom/dressroom.css, components/gnosis/dressroom/*, lib/gnosis/dressroom/*, public/dressroom/*, 관련 tests/*.

제한 수정: app/gnosis/write/page.tsx에 명시적 진입/초안 회복/코디 첨부. 코디 카드가 필요할 때 app/gnosis/[id]/page.tsx에 지원 여부를 검사한 렌더링만 추가한다. 기존 글과 기존 item_data는 그대로 읽을 수 있어야 한다.

엔진 추가 시 package.json/package-lock.json 변경. 전역 layout/IRIS/native/인증/API/DB/migrations는 이번 단계 수정 대상이 아니다. 공통 문서 갱신은 제품 구현이 확정된 실제 범위만 수행한다.

## 7. 화면·오류 기준

프로젝트 전역 테마와 rem 글자 기준을 사용한다. 320/390px에서는 뷰어와 편집 패널을 세로 배치하고 768/1280px에서 옆으로 나눈다. 목록 외 가로 스크롤을 만들지 않는다. 닉네임/제목은 단어 단위 줄바꿈, 각 조작은 키보드·바깥 클릭·Escape 규칙을 따른다.

로딩/모델 없음/호환 불가/카탈로그 불일치/JSON 손상/저장 용량 초과/WebGL context loss를 구분한다. 실패를 예시 성공 데이터로 바꾸지 않는다. 원래 코디와 작성 초안은 사용자가 명시적으로 버릴 때까지 보존한다.

## 8. 검증과 단계 완료 정의

- 순수 검사: 문서 크기·스키마·알 수 없는 ID·잘못된 색상·깨진 JSON·버전 불일치·이전 상태 보존.
- 실제 브라우저: 부위 선택·색상 변경·저장/새로고침·내보내기/가져오기·본문 초안 왕복·느린 모델 로드 순서·실패 회복.
- 320/390/768/1280px, PC18/20/22px 및 밝고 어두운 테마. 실제 GPU 렌더링과 WebGL 불가 경로는 구분해 기록한다.
- 관련 테스트·독립 TypeScript·변경 범위 lint·Production build. 기존 코드에 오류가 있으면 기준선과 신규 오류를 구분한다.
- 실제 게임 모델 착용은 모델이 확보되어 시각 검증한 경우에만 완료로 표시한다. JSON과 UI만으로 게임 착용 완료를 주장하지 않는다.

## 9. 작업 격리와 병합

브랜치 codex/gnosis-dressroom, 기준1d8e3749f306456bea1c2a7b2e05da813b98e5fa. 기존 IRIS 폴더·브랜치·미커밋 파일은 보존한다. 집의 미전송 작업을 현재 작업에 존재한다고 가정하지 않는다.

분리 작업 폴더의 node_modules/.next/.env.local은 Git 제외. .env.local에는 기존 공개 Supabase 연결 설정2개만 복사했고 서버키/로그인코드는 복사하지 않았다. 로컬 서버는127.0.0.1:3100, 기존 IRIS 서버와 별개다.

공식 push는 한설의 명시 요청 때만 한다. 통합은 집 변경을 먼저 보존한 뒤 최신 원격을 받아 드레스룸 커밋과 경로를 대조한다. 같은 파일/잠금 파일/전역 문서 충돌을 덮어쓰지 않고 양쪽 의도를 반영한다. main 병합·운영 DB·배포는 별도 승인 전 실행하지 않는다.
