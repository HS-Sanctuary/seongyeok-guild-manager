# IRIS 생텀 전용 앱 전환 설계

작성: 2026-10-05 KST · 영겁

상태: 2026-10-05 한설이 “좋아”로 설계를 검토 승인했다. 구현 계획 검토 및 실행 방식 승인 전 제품 코드 전환을 시작하지 않는다. 미커밋이며 운영 DB 변경·배포 승인이 아니다.

## 1. 목적과 승인 범위

반복적인 브라우저 열기·읽기 승인·쓰기 승인 때문에 편의보다 번거로움이 앞서는 현재 흐름을 없앤다. IRIS에서 생텀 계정으로 로그인하고 본인 캐릭터를 선택해 숙제를 확인·수정한다. 웹 생텀과 IRIS는 같은 서버 저장 기록을 사용한다.

- 로그인 유지, 로그아웃, 여러 계정을 기억해 한 계정씩 전환하는 방식.
- 직접 캐릭터 선택. 게임 닉네임 자동 식별 또는 게임 계정 인증을 주장하지 않는다.
- 변경은 화면에 즉시 반영하고 마지막 관련 조작 후 15초 자동저장.
- 캐릭터를 바꿔도 이전 캐릭터 변경은 별도 저장 대기분으로 보존한다.
- 지금 저장·변경 버리기 버튼과 저장 상태 안내 유지.
- 일간 KST06시, 주간 월요일 KST06시 기간 경계 및 동시 수정 보호.
- 새 화면은 둥근 카드/버튼·6테마를 기준으로 설계. 전체 디자인 재작업은 저장 기능 안정화 이후.

멀티 계정은 하나의 활성 계정을 전환하는 권장안으로 제시했고 사용자가 그 방향으로 진행을 승인했다. 동시 여러 계정 실행은 이번 범위가 아니다. 계정 전환과 캐릭터 전환의 저장 규칙은 다르다.

## 2. 현재 확인한 기반과 제한

- 현재 IRIS는 PowerShell/WinForms + owned Node 서버이며 설치형 완성 앱이 아니다.
- `lib/server/sanctumSession.ts`와 auth login/session/switch/logout API에 서버 세션·HttpOnly 쿠키 기반 인증이 있다. 현재 서버 세션 유효기간 상수는 30일이며 영구 로그인으로 표현하지 않는다. 쿠키 갱신만으로 서버 세션 만료가 연장된다고 가정하지 않는다.
- 현재 IRIS 쓰기는 브라우저 relay·별도 쓰기 동의·선택 버전 단일 큐에 의존한다. 다른 캐릭터의 지연 저장을 그대로 지원한다고 가정하지 않는다.
- `lib/server/irisKronosWrite.ts`는 서버 본인 확인 및 JSON 필드 조건부 갱신으로 다른 기록을 보존한다. 기존 기간 검증을 재사용한다.
- 한설이 오버레이 숙제 저장→웹 반영 1건을 확인했다. 이후 깜빡임/긴 저장 지연 수정은 자동192/192·타입 검사 통과, 수정 실행본의 실제 게임 위 재검증은 아직 대기다.
- 자동 클래스 레벨 전체 읽기·시낙시스 상태·게임 자동 명령은 이번 전환의 완료 조건이 아니다.

## 3. 선택한 구조와 대안

권장: Windows 앱에 생텀 전용 로그인/숙제 웹 화면을 내장하고 기존 HTTPS 서버 인증 API를 사용한다. WebView2를 우선 검증 후보로 삼는다. 사용자는 외부 브라우저 탭을 계속 열어두지 않는다. native 게임 읽기 위젯은 분리해 보존한다.

대안 A: 기존 외부 브라우저 relay에서 승인만 합친다. 작업량은 작지만 사용자가 지적한 탭 유지·재연결 번거로움을 근본적으로 해결하지 못한다.

대안 B: native HTTP 클라이언트에 별도 로그인 토큰과 인증 체계를 만든다. 독립성이 있지만 새 토큰 발급·보관·폐기 경로와 보안 부담을 늘린다. 초기 전환에서는 택하지 않는다.

권장안의 실행 가능성 게이트:

1. 현재 Windows 런타임에서 WebView2 로딩·앱 전용 프로필·쿠키 재실행 유지·기존 로그인 API·정상 종료를 합성/로컬 환경으로 확인한다.
2. 현재 PowerShell에서 안정적 내장이 어렵다면 .NET 앱 호스트 시제품까지 계획 범위에 포함하되, 기존 실행본을 교체하거나 설치물을 배포하지 않는다.
3. 실패하면 런타임/호스트 대안을 보고하고 설계를 다시 검토한다. 임의 패키지 복사나 새 인증 프로토콜로 우회하지 않는다.

화면/인증·저장 상태 관리는 앱 전용 웹 화면이 소유한다. native와 웹에 독립적인 쓰기 큐를 동시에 만들지 않는다. 웹→native 브리지는 표시/숨김·창 위치 등 좁은 기능만 제공하며 origin·메시지 형식·앱 세대 검증이 필요하다. 로그인 코드·쿠키를 메시지로 내보내지 않는다.

## 4. 로그인과 계정 전환

- 사용자가 앱 안에서 기존 대표 닉네임/접속 코드를 직접 입력한다. 로그·설정 파일·채팅에 코드를 보관하지 않는다.
- 앱 전용 보호된 프로필을 사용한다. 사용자의 Chrome/Edge 쿠키를 추출하거나 복사하지 않는다. 서버 키와 DB 직접 연결 권한을 앱에 넣지 않는다.
- 허용한 정확한 서비스 HTTPS origin만 인증/쓰기 화면을 열 수 있다. 개발 localhost는 개발 모드에서만 허용하고 운영 로그인 프로필과 분리한다. 임의 외부 페이지에는 native 브리지 접근을 주지 않는다.
- 로그인 유지 선택을 제공하고 유효한 세션만 복원한다. 만료·승인 취소 시 쓰기를 멈추고 재로그인을 안내한다. 오프라인에서는 저장 완료라고 표시하지 않는다.
- 계정 전환 전에 새 수정 접수를 잠그고 이전 계정의 저장 요청을 완료/결과 확인한다. 미전송 변경은 이전 계정의 보호된 대기함에 남긴다. 결과 불명확 요청은 재전송하지 않는다.
- 전환 후 이전 계정 대기분을 새 계정 쿠키로 저장하지 않는다. 이전 계정으로 돌아와 인증을 확인한 뒤 대기분을 재개한다. 동시에 두 계정이 자동저장하는 기능은 없다.
- 로그아웃은 자동저장을 중지하고 미저장 변경의 저장 또는 보관/폐기를 안내한다. 명시적 폐기 없이 조용히 지우지 않는다. 서버 세션 폐기는 기존 logout API 정책을 따른다.

## 5. 캐릭터별 15초 저장 규칙

저장 대기분은 `환경 + accountId + characterId + taskId + periodKey`에 귀속된다. 화면에 현재 보이는 캐릭터와 독립적이다. 표시 닉네임만으로 대상을 결정하지 않는다.

1. 체크/증감은 로컬 화면에 즉시 반영. 같은 항목의 미전송 변경은 원래 기준값을 유지하고 마지막 희망값으로 합친다.
2. 해당 캐릭터의 마지막 편집에서 15초 타이머를 다시 센다. 변경이 원래 값으로 돌아오면 미전송 항목을 제거하고 쓰기를 하지 않는다.
3. 수정 대기 중인 캐릭터에서 다른 캐릭터로 전환하면 이전 대기분을 보존하고 전환 시각에서 15초 뒤 저장 예약한다. 새 캐릭터 조작은 이전 캐릭터의 타이머를 다시 미루지 않는다. 수정이 없는 전환은 쓰기를 만들지 않는다.
4. 같은 계정 내 각 캐릭터의 타이머는 독립적이고 네트워크 저장은 직렬 처리한다. 늦게 끝난 응답은 원래 캐릭터에만 적용한다.
5. 지금 저장은 선택된 캐릭터의 대기분을 즉시 예약한다. 다른 캐릭터 대기분은 별도 표시한다. 변경 버리기는 선택된 캐릭터의 미전송 변경만 폐기한다.
6. 저장 중 추가 편집은 다음 리비전에 보존한다. 늦은 응답으로 새 편집을 지우거나 이전 값으로 되돌리지 않는다.

안내: “마지막 변경 후 15초 뒤 자동으로 저장됩니다. 바로 저장하려면 ‘지금 저장’을 눌러 주세요.”

상태: 변경 없음 / 저장 예정(남은 초) / 저장 중 / 저장 완료 / 연결 대기 / 충돌 / 결과 확인 필요 / 이전 기간 변경.

15초는 의도한 자동저장 대기이며 지금 저장의 전송을 지연시키는 주기가 아니다. 전송 후 서버 검증 지연과 자동저장 타이머를 화면에서 구분한다.

## 6. 저장 안전과 복구

- UI는 DB에 직접 쓰지 않고 로그인된 같은 origin의 서버 API를 사용한다. 서버가 매번 실제 계정·소유권·기간·허용 항목·값 범위를 검증한다.
- 기존 단일 항목 검증/조건부 갱신을 기반으로 변경 항목만 저장한다. 캐릭터 전체 스냅샷을 덮어쓰지 않는다.
- 초기 버전의 여러 변경은 한 번의 사용자 저장 묶음으로 직렬 처리하되 부분 성공을 표시한다. 요청 수를 하나로 줄이기 위한 batch API는 별도 계획·테스트 대상이며 이미 구현된 것으로 표현하지 않는다. DB 구조 변경을 전제로 하지 않는다.
- 웹과 IRIS의 동시 수정 충돌은 최신값을 확인해 표시하고 강제 덮어쓰지 않는다.
- 요청이 서버에 도착했는지 불명확하면 먼저 같은 캐릭터/기간의 최신값으로 확인한다. 확인 불가 시 결과 확인 필요로 보류하며 POST를 반복하지 않는다. 이미 희망값이면 완료 처리한다.
- 대기분은 Windows 사용자 범위로 암호화된 로컬 저장소에 보관하고 손상/과대 데이터 검증·원자적 교체를 적용한다. 로그인 코드·서버 키·브라우저 쿠키는 넣지 않는다. 삭제된 계정/캐릭터·다른 환경의 대기분을 자동 재생하지 않는다.
- 앱 재실행은 자동저장을 바로 재생하지 않고 세션·소유권·기간·최신 기준값을 확인한 뒤 재개한다. 이전 프로세스의 in-flight는 결과 불명확으로 복구한다.
- 종료 시 미저장/저장 중/불명확 상태를 알리고 지금 저장 후 종료 또는 안전 보관을 제공한다. 강제 종료가 성공 저장을 뜻하지 않는다.

## 7. 초기화 및 요청량

- 기존 KST06시 일간/월요일06시 주간 규칙을 공유한다. 스케줄러 실행 성공 여부만 믿지 않고 저장 요청 자체에서 변경 당시 기간과 현재 서버 기간을 비교한다.
- 05:59 편집이 06:00 이후 도착하면 새 기간에 쓰지 않고 이전 기간 변경으로 분리해 안내한다. 게임 날짜·시간대를 클라이언트 현지 요일로 계산하지 않는다.
- 유휴 15초마다 DB 쓰기를 하지 않는다. 변경 없는 캐릭터 조회도 무한 반복하지 않는다. 시작/캐릭터 선택/복귀/저장 결과 확인과 제한된 갱신 정책을 둔다.
- 저장 묶음마다 전체 계정/전체 카탈로그를 재조회하는 N+1을 피한다. 카탈로그는 유효성 갱신 정책과 함께 재사용하되 서버 권한·기간 검사를 생략하지 않는다.
- 실제 이그레스/요청 수와 저장 확인 지연은 합성 측정 및 사용자 검증으로 기록한다. “15초 자동저장이므로 저렴하다” 또는 총 저장1초 보장은 하지 않는다.

## 8. UI 및 단계적 전환

- IRIS 센터 아래 크로노스의 로그인/캐릭터 선택/숙제 체크보드를 명확히 구분하고 관련 창의 중복 생성 방지를 갖춘다.
- 선택 계정·캐릭터 및 다른 캐릭터의 저장 대기 수를 지속 표시한다. 배경 상태 조회로 행을 폐기/재생성하지 않고 변경 부분만 갱신한다. 스크롤·접힌 항목·초점을 보존한다.
- 6테마·둥근 패널/버튼·긴 닉네임 전체 표시·키보드 조작을 기준으로 신규 화면을 만든다. 전체 게임 위젯 디자인 개편은 다음 단계다.
- 기존 게임 읽기 기능과 단축키를 보존한다. 게임 실행 자동 감지/자동 시작은 사용자 선택형 후속 기능이며 이번 구현에서 OS 시작 설정이나 게임 조작을 추가하지 않는다.
- 새 경로가 로컬 검증되기 전 기존 bridge 파일/기능을 삭제하지 않는다. 기본 경로 전환은 테스트 및 한설 확인 후 수행한다.

## 9. 완료 조건과 다음 승인

합성 자동 검증:

- 15초 타이머 재시작, 원래 값 복귀 시0쓰기, 지금 저장, 미전송 폐기.
- 캐릭터 A→B 전환 후 A 저장, B 편집이 A를 지연시키지 않음, 늦은 A 응답이 B를 변경하지 않음.
- 저장 중 편집, 부분 성공, 동시 웹 충돌, 응답 유실·결과 불명확·중복 저장 방지.
- 계정 A→B/로그아웃/만료 중 대기 및 응답 격리, 타인 캐릭터 요청 거절.
- KST06시 일간/월요일 주간·해외 OS 시간대·절전 후 복귀·기간 지난 복구.
- 로컬 큐 손상·중복 프로세스·정상/강제 종료·재시작 복구.
- 유휴/연속 편집의 요청 수 및 안정적 컨트롤·스크롤·초점 보존.

한설 수동 검증:
