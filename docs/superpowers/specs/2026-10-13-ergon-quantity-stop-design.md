# ERGON 수량 기반 작업·실제 중지·간결한 실행 화면

상태: **2026-10-14 한설 A 구현 승인 / A 로컬 후보·합성검증 완료 / 실제시험·B 미완료**. 한설이 서면 검토 안내 뒤 ‘진행하자’로 직접 구현을 승인했다. 구현계획/실행 근거는 `../plans/2026-10-14-ergon-quantity-stop.md`. 새 소비시험·운영배포 승인은 별도다. 아래는 설계 기준이며 B 전체가 완료된 것은 아니다.

## 1. 사용자에게 달라질 동작

- 직접 채집은 ‘이번에 추가로 캘 수량’이다. 시작 재고가45이고 추가15를 선택하면 목표 가방수량은60이다. 원래 보유분을 다시 캐지 않는다.
- 최종 가공/제작품은 ‘이번에 추가로 만들 수량’으로 입력한다. 산출량과 제작횟수는 별도 표시한다. 예를 들어1회3개 산출/목표10개라면4회·예상12개이며 남는2개도 알린다. 이 숫자는 설명 예시이지 실제 레시피가 아니다.
- 수량을 직접 입력하거나 ±로 조정한다. 계획을 저장/수정한 것만으로 게임을 조작하지 않는다. 진행 중 목표와 비용승인은 불변이며 수량변경은 대기계획에만 반영한다.
- ‘지금 중지’는 IRIS가 시작한 현재 채집의 실제 중지 요청이다. 동시에 후속 작업도 금지한다. ‘다음 작업 중지’는 별도 보조 동작으로 구분하며 현재 채집을 멈춘 것처럼 표현하지 않는다.
- 진행 화면의 기본 정보는 품목/현재상태/추가확보량/목표/남은양/날개/주조작이다. 반복된 설명·내부코드·고정된 개발단계 안내는 펼치는 자세히 영역으로 옮긴다. 막힌 이유는 해당 위치에 짧은 한국어로 표시한다.

## 4. A — native 목표·중지 계약

### 요청과 비용

- 고정 typed bridge만 확장한다. capabilities에 수량채집/현재작업중지 지원을 명시하고 구앱에는 새 실행UI를 활성화하지 않는다. 스키마/파서/개발native를 함께 갱신하되 구형 보호기록 읽기는 보존한다.
- 준비 intent에 추가수량을 결합한다(초기1..100). 시작가방재고/추가목표/가방최종목표/품목/환경/계정/캐릭터/epoch/nonce/날개한도를 native가 검증·동결한다. 이 값은 사용자최종확인에도 표시한다.
- 현재 execute_gathering 입력은 공식 displayName만이다. 임의 target/quantity 인자를 만들지 않는다. 100초과 계획은 예상 최소호출수를 보여줄 수 있지만 A에서는 한 소비명령으로 제한하고 나머지는 명시적 새확인 대상으로 남긴다.
- 보유량 조회는 정확한 이름·category Ingredient·inventory·잠금해제만 사용, 동일이름 이종분류/중복자료/누락/오래된조회는 미확인이다. 실패를0이나 목표달성으로 처리하지 않는다.

### 진행 관측

- 긴 실행 CLI와 별도로 native가 약1초 간격으로 품목재고를 읽는다. 단일flight이며 완료된조회 다음에 간격을 둔다. 기본8초 읽기상한/1MiB 제한 유지. 큐나 UI polling과 별개로 실행 native가 수명을 소유한다.
- 목표가방수량=시작가방수량+추가수량, 추가확보=max(0,현재−시작). 계산은 안전정수/범위검사. 원래 재고를 진척으로 세거나 조회누락을0으로 합산하지 않는다.
- 목표에 닿으면 중지 요청을 세우고 다음 소비명령을 금지한다. 벌목 묶음/조회지연/Stop 가능한 타이밍 때문에 초과확보 가능, 실제확보와 초과량을 표시한다. **정확히1개 보장/100개보다 반드시 적게 캔다는 약속은 하지 않는다.**
- 화면 숨김 뒤에도 이미 승인한 실행의 목표감시와 결과관측은 계속한다. 재시작은 자동재개하지 않고 기존 inflight→unknown 안전규칙을 유지한다.

### 실제 중지와 완료

- stop 요청은 현재실행 requestId에 결합한다. 현재작업 없음/종료됨/다른계정·문맥/다른requestId/중복요청은 게임명령0으로 처리한다.
- 소비CLI가 실제응답을반환하는즉시 `performInFlight`를해제한다. 이후후속재고조회때문에전체actor가busy여도 stop은보내지않는다. 모든stop시도는이실행중표식을읽기전/전송직전에재검하며, native가새실행을받지않는동안에도늦은stop으로다른행동을건드리는창을줄인다.
- 기존 일반 bridge busy 차단과 소비실행 잠금 때문에 stop이 긴 실행 뒤에 줄서지 않도록 제한된 별도 control 경로를 만든다. **busy이므로 stop까지 막는 가드**를 만들지 않는다. origin/epoch/payload/IRIS 소유실행 검사는 유지한다.
- 공식 stop_action에는 작업전용 ID가 없다. ‘IRIS 실행세션 연결’은 게임의 행동소유권 증명이 아니다. 최초실행확인 때 목표감시중지를 포함한 영향과 타앱 동시실행 금지를 짧게 알린다. 연주/다른수동행동/문맥교체 등 교체징후나 활동조회 미확인이 있으면 자동중지를 보내지 않고 현재게임 Stop 사용을 안내한다.
- 이내용은 기존설계의 소유권불명자동Stop금지 경계를 바꾸는 제안이다. **현재게임행동을멈출수있는영향/다른앱명령및수동조작과동시사용하지않겠다는조건을확인한 목표감시중지 승인**이없는경우 자동Stop은off다. 이기능개발동의와개별실제게임중지/자동목표중지동의를혼동하지않는다. 공식행동ID부재의잔여경합위험은완전히제거됐다고표현하지않는다.
- 현재 Mode.MainButtonState=Stop 등 실제중지가능상태를 재확인하여 고정 stop_action을 전송한다. 불확실/Hide 타이밍이면 ‘중지 대기’로 표시한다. invalid_state일 때만 같은실행이 살아있고 새활동조회가 Stop인 조건으로 최대2회 추가시도(총3회/최대10초 대기). 시간초과/전송불명은 중지확인불가, 무한재전송 금지.
- ‘중지 요청됨’과 ‘중지 완료’는 다르다. stop 응답만으로 잠금을 풀지 않는다. 원래 소비CLI 최종응답·후속재고/날개·활동을 함께 관측한 뒤 terminal을 결정한다. 원래CLI가 종료되지 않은 동안 후속소비0, CLI를 kill해서 게임중지완료로 처리하지 않는다.
- 공식 result=stopped가 오고 비용/재고 관측이 일관되면 ‘중지됨’으로 보존한다. 목표도달로 요청한 중지는 ‘목표 확보 완료’와 실제확보/초과량을 함께 표시한다. 사용자가 목표전 중지하면 부분확보와 수동중지를 표시한다. 오류·accepted+error·관측불명·중지응답불명은 unknown을 유지하고 재시도/체인을 막는다.
- DPAPI 보호원장에 중지요청/이유/관측결과를 기록하는 새형식을 설계한다. 기존schema/terminal읽기·환경격리·300건/30일·inflight보존·파일잠금 유지. 구형파일의 미확정을 자동해제/삭제하는 마이그레이션은 금지한다.

## 5. A — 화면 구성

- 기존 네 메뉴/세 상위기능 이름을 보존한다. 작업계획 목록은 검색+품목+수량스테퍼+추가, 실행은 선택한계획의 한 카드로 만든다. 전체 목록과 실행안내를 한 화면에 늘어놓지 않는다.
- 카드: 품목 / 추가목표 / 확보량·남은양 / 예상·실제날개 / 현재상태. idle은 ‘준비’, 승인전은 ‘시작/취소’, running은 항상 보이는 ‘지금 중지’, stopping은 비활성 ‘중지 확인 중’, terminal은 결과와 ‘새 계획’이다.
- 현재 작업 중지와 다음작업중지를 한 동일버튼으로 숨기지 않는다. 초기A는 자동후속 없음이므로 ‘지금 중지’가 주조작이다.
- 한 번의 준비와 native 최종확인을 유지하되 중복된 긴안내를 제거한다. 정확캐릭터·대상·수량·한도는 native 확인창에서 빠짐없이 보여준다.
- 내부에러코드 대신 읽기쉬운 짧은 사유, 자세히를 펼치면 시각/검사상태/소량초과주의를 표시한다. 아직미연결 같은 과거문구를 실제연결된기능에 남기지 않는다.
- 준비숫자를실제비용으로보여주지않고, 조회시각이오래되면 표시한다. 전역6테마/currentColor SVG·6..22pt·320/390/720폭·키보드·밖클릭/Escape·초안/선택보존을 재사용한다. 독립HUD/새창/모바일원격은 추가하지 않는다.

## 6. B — 부족분과 재료표

### 2026-10-15 B1 — 여러 목표의 통합 대기열과 시설 관측

- 한설이 점검 중 실게임 검증은 저녁 영겁에게 맡기고 설계 갱신 후 즉시 구현을 요청했다. 기존 관제실·단일 실행은 유지하고, 먼저 보관한 여러 목표 전체를 한 번에 계산한다. 자동 소비 체인 완성이나 실제 unknown 해제 승인으로 해석하지 않는다.
- 목표는 모두 추가 생산량이다. 여러 목표·하위 경로가 같은 가방 재고를 각자 재사용하지 않도록 한 예약표로 계산하며, 예상 산출의 단위 잔량만 별도 예상분으로 재사용한다. 예상분을 실제 확보로 표시하지 않는다. 여러 경로가 같은 재료를 만들더라도 서로 다른 목표 결과물 자체를 다른 목표의 재료로 빼앗지 않는다.
- 최대 50개 보관 계획, 목표 1..1,000,000, 통합 확장 최대 32개 노드/깊이 4. 넘는 경우 잘린 결과를 전체 완료처럼 표시하지 않고 안내·차단한다. 기존 단일 읽기전용 미리보기 깊이 8은 그대로 유지한다. 모든 목표별 원본은 보존한다.
- 참고 재료표 조회는 통합 미리보기를 펼쳤을 때만, root 포함 최대32품목을 직렬 조회한다. 완료·실패 결과를 한 화면 범위에서 기억하고 자동 재시도하지 않는다. 계정/캐릭터/환경 변경·잠금·화면 이탈 시 늦은 응답을 폐기한다. 이 경로는 소비 명령을 호출하지 않는다.
- 시설 관측은 공식 works 조회에 나타난 등록 작업만 집계한다. 등록수는 시설 정원이 아니다. 완료 여부 미확인/오래된 조회는 수령 타이밍 미확인. 확인된 등록 작업의 절반 이상이 완료되면 수령 검토를 안내하되, 전체 수령의 다른 품목 포함·비용·실제 정원/빈자리 계약을 확인하기 전 자동 수령·재등록은 하지 않는다.
- 통합 대기열에서 목표 수량 수정·선택·제거와 부족분을 함께 확인한다. 실행 버튼은 기존 선택 작업의 준비/native 최종 확인만 사용한다. 자동 일괄 시작 버튼을 보이는 것만으로 연결된 것처럼 만들지 않는다.
- 시험: 두 목표 공유 재고·각 목표 추가량·단위 잔량·부분 재료표·잠금/창고/미해금·깊이/노드/안전정수, 시설7등록4완료/3완료·미확인·오래된 조회·다른 품목 수령 범위, 실제 React 목표 수정/두 캐릭터 늦은 참고응답/잠금 중 IO0/반응형·큰글자. 기존 실제 실행 보호·수량/중지 회귀를 유지한다.

### 2026-10-15 B1 후속 — 추가 제작 목표와 단일 명령 분리

- 기존 수량 제작은 목표가 5회 산출을 넘으면 실행 준비도 막혀 있다. 목표20개를 입력하면 같은 목표 안에서 다음 요청 최대5회만 준비할 수 있도록 분리한다. 자동 반복은 하지 않으며 매 요청 기존 준비/native 최종 동의를 유지한다.
- 한 제작 명령의 날개5/제작횟수1..5 계약, 묶음 최대5명령·날개25·다음 준비기한5분을 보존한다. 수량입력은 추가 결과물1..1,000,000이다. 한 명령의 초과 산출은 진척에 실제 확인량으로 반영한다.
- 해당 화면에서 보낸 requestId와 계정/캐릭터/종류/품목·확인된 craftCount/output/expectedOutput 및 정확 debit5가 일치하는 completed만 목표 진척으로 반영한다. 장비의 조회되지 않는 보유량을0으로 만들지 않으며, 기존 보유량·과거 이력·중복된 같은 응답은 진척이 아니다.
- running/registered/rejected/unknown/응답불명은 완료 수량을 늘리지 않는다. 현재 요청이 미확정이면 다음 준비를 막고 원래 원장을 유지한다. 사용자가 목표/품목/캐릭터를 바꾸면 별도 추가 목표가 되며 이전 실행을 새 목표의 진척으로 가져오지 않는다.
- 목표달성 뒤 같은 목표로 재준비하지 않는다. 사용자가 새 목표로 명시적으로 다시 시작할 수 있게 한다. 메뉴 이탈은 다음 준비를 중지하지만 이미 요청한 명령의 완료 관측을 버리지 않는다. 새 묶음은 완료량은 유지하고 횟수/날개/5분 한도만 새로 확인한다.
- UI 진척은 메모리의 세션 관측이다. 앱 재시작 시 자동 재개/이력으로 임의 복원하지 않고 새 목표 준비 전 안내한다. 신뢰 가능한 영속 작업 큐 및 무인 native chain은 후속 B2이며 이번 후보의 완료 주장에 포함하지 않는다.
- 확인된 진척은 동일 계획ID/캐릭터/원래 목표의 임시 진척으로 부모 관제실에도 전달한다. 큐·선택 재료는 `max(0,원래 추가목표−확인된 산출)`로 계산하고, 저장된 원본 목표는 유지한다. 완료한 목표는 부족분 확장 대상에서 빼되 화면의 원래 수량/완료량은 표시한다. 명시적 새 추가 목표는 진척0으로 재설정한다. 목표 편집·계정/캐릭터 전환은 별도 범위이며 이전 결과를 다음 목표에 합산하지 않는다.

- 계획원천은 ‘현재1회부족분’과 ‘알려진재료표’를 분리한다. 관찰누적/사용자검증자료의 출처·시각·경로서명·충돌·완전성 상태를 보존한다. 여러출처의 일치도 전체재료표 완전성 증명은 아니다.
- 전체재료표가 확인되지 않으면 ‘확인된 부족분’만 보여주고 여러회전체총량/자동체인 실행을 막는다. 불완전목록의 빈 배열을 모든재료충분/비용0으로 해석하지 않는다. 부족품 채집만을 사용자가 개별 선택하는 A의 수동흐름은 가능하다.
- 최종품추가Q/1회산출P이면 필요한횟수ceil(Q/P), 재료별전체필요량=회당필요량×횟수. 잠김제외가방재고와 검증된경로별이용가능재고를 빼 부족분 계산한다. 창고는 별도로 표시하며 공식사용가능/이송비용이 확인되기 전 무조건가방과합산하지 않는다.
- 최종품추가수량과 추가채집수량, 목표보유수량을 혼합하지 않는다. B 최초는 ‘추가로 만들기’ 한 의미로 통일하고 총보유량모드는 별도 후속이다.
- 경로는 레시피이름뿐 아니라 종류/산출/재료서명으로 식별한다. 동명경로는 사용자선택 없이자동결정하지 않는다. 부족품의공급경로가없으면 상점/수동확보/미확인으로분리한다. 매입/자동구매는 새승인없이 실행하지 않는다.
- 순환/깊이최대4/동명혼동/자료충돌은 의존계획실행차단. 여러갈래에서 같은재고를 중복사용하지 않도록 계획내재고예약표를 사용하고 예상부산물을 확보된재고로미리세지않는다. 원자적으로전체미리보기를 계산해 절반계획만저장하지않는다.
- 선행가공은 등록만으로 공급완료가 아니다. 등록→생산대기→시설완료분전체수령확인→실재고확인→후속제작을 연결한다. 다른품목포함시설전체수령의 대상/비용불명과 시설슬롯계약미확인은 자동강제하지않는다.
- 재료표·공식실측없음이 B의현재경계이며, 수동검증/자료출처확정 방식은 B 실행계획에서 먼저 정한다. 외부앱의레시피번들을몰래가져와완성기능으로출시하지않는다.
