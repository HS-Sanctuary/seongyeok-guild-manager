### 한설이 먼저 확인할 요약

제작 명령이 끝나도 실제 수량을 모르면 진행을 멈춘다. 사용자가 **이번 제작으로 추가 확보한 개수**를 확인하면, 그 요청에 대한 최신 확인량만 진척으로 계산한다. 0개도 명시적 확인이며 미확인과 다르다.

목표·요청·정정 이력을 PC의 별도 암호화 진행 기록에 함께 저장한다. 기존 실행 안전 원장은 그대로 두고, 두 기록의 연결이 맞지 않으면 완료나 추가 소비를 허용하지 않는다. 파일 복구도 곧 실행 허가가 아니다. 전체 자동 생산·가공 반복 관리자는 만들지 않는다.

## 2. 핵심 불변 조건

1. 예상 산출·제작 횟수·명령 completed는 확인 수량이 아니다.
2. 확인 수량은 **요청별 최신 유효 확인값의 합**이다. 확인 이벤트를 전부 더하지 않는다.
3. null은 미확인, 0은 명시적으로 확인한 0개다. 누락/손상/알 수 없는 결과를 0으로 바꾸지 않는다.
4. 수량 정보, 실행 안전 상태, 저장/복구 상태, 목표 운영 상태는 서로 독립적이다. 하나를 확인해 다른 잠금을 풀지 않는다.
5. 진척 변경과 중복 방지·정정 이력은 **동일한 한 번의 파일 커밋**에 들어간다.
6. 저장 성공 ACK 전에는 진척·완료·재료 예약을 갱신하거나 성공을 안내하지 않는다.
7. native 원장은 실행 사실의 권위다. 진척 파일은 이를 변경하거나 success를 주입하는 경로가 아니다.
8. 복원·결과 확인·계속하기·목표 삭제는 게임 명령 실행 동의가 아니다. 기존 nonce·lease·최종 동의·재검증을 생략하지 않는다.
9. 목표/환경/계정/캐릭터/요청 연결을 모두 대조한다. 같은 품목명만으로 기록을 합치지 않는다.
10. 사용자 확인량은 `사용자 확인`이며 공식 검증 수량으로 표시하지 않는다. 확인 생산량이 현재 가방 보유량이라는 보증도 하지 않는다.

## 3. 저장 책임과 대안

**선택: native 전용 암호화 진행 sidecar 1개/환경.** 후보 파일명은 `ergon-progress-v1.dpapi`다. 실제 파일은 이번에 만들지 않는다. 계정·캐릭터 ID를 파일명에 넣지 않고 암호화된 내용에서 분리한다.

- localStorage 확장안: 구현은 작지만 앱의 암호화·파일 커밋·native 요청 대조 경계와 분리되어 진척의 권위 저장소로 선택하지 않는다.
- 기존 안전 원장/숙제 대기함 확장안: 다른 보호·동기화 책임과 섞이므로 선택하지 않는다.
- 별도 sidecar: 데이터 목적만 분리하고 기존 native bridge·DPAPI·파일 잠금 방식을 재사용한다. 브라우저와 native에 두 개의 권위 진척 저장소를 만들지 않는다.

UI 메모리는 마지막 저장 ACK의 읽기 모델과 미저장 입력 초안만 가진다. UI가 계산한 전체 goal JSON으로 파일을 교체하는 API는 금지한다. 서버·클라우드·원격 동기화는 사용하지 않는다.

## 4. 데이터 계약 v1 — 제안, 구현 전

### 4.1 문서와 목표

문서: schemaVersion, environment, storeId(UUID), revision(단조 증가 정수), 이전 커밋 연결 digest, goals, attempts, auditEvents. 커밋 연결 digest는 정합성 대조용이지 악의적 로컬 롤백을 막는 외부 신뢰 기준은 아니다.

목표:

- goalId: 재사용하지 않는 UUID. 원래 sourcePlanId와 구분한다.
- environment, accountId, characterId, action/목표 품목의 정확한 명칭, 목표 종류(`추가 생산`)와 targetQuantity.
- 원래 목표 정의와 생성 시각. targetQuantity는 1~1,000,000 정수이며 현재 제품 계약을 유지한다.
- parentGoalId/rootGoalId: 선행 제작·가공과 최종 목표의 관계. React의 임시 UUID만으로 부모를 찾지 않는다.
- lifecycle: active / paused / cancelled / archived. 목표 수량 달성 여부는 별도 파생값이다.
- 목표 정의·상태 변경의 이벤트 연결. 이미 요청이 붙은 목표의 품목/수량을 조용히 덮어쓰지 않는다.

실행 요청이 붙은 후 계획 초안의 수량/품목이 달라지면, 기존 목표를 보존하고 ‘새 목표로 적용’을 명시적으로 선택한다. 새 goalId를 사용하고 옛 확인량을 자동 이전하지 않는다. 실행 전 초안 편집은 기존 계획 편집으로 유지한다.

### 4.2 실행 시도와 가공 회차

실행 시도는 requestId(기존 nonce), goalId, 전체 소유 범위, action/정확한 품목, 준비 시각·기한, native가 동결한 craftCount/outputPerCraft/expectedOutput, 준비·제출·종료 관측 정보를 가진다. UI가 전달한 completed나 비용을 실행 증거로 신뢰하지 않는다.

- `processingRound`: **목표에 연결된 가공 등록 시도의 회차**. 관련 가공 요청을 연결할 때 저장소에서 순번을 부여하며, 취소된 순번도 재사용하지 않는다.
- 등록 성공 횟수는 registered로 대조된 요청 수로 별도 계산한다. 회차 번호·등록 횟수·실제 생산/수령 수량을 혼동하지 않는다.
- 제작 요청의 craftCount는 ‘이번 제작 시도 횟수’이며 가공 회차가 아니다. 가공과 무관한 요청의 processingRound는 null이다.
- 현재 공식 안정 work/job ID·시설 정원/빈자리 계약이 없으므로 회차를 실제 시설 작업 ID나 슬롯 번호로 표시하지 않는다.
- 다음 구현의 가공 범위는 기존 수동 등록 경로의 요청 연결·회차 기록까지다. 자동 재등록·시설 회전·자동 수령·가공 예상량의 완제품 진척 전환은 제외한다.

한 requestId는 한 goal에만 귀속된다. 같은 요청을 선행품과 최종품 양쪽 진척에 적용하지 않는다. 최종품과 다른 선행품의 확인량은 최종품 확보량에 더하지 않는다.

### 4.3 확인·정정 이벤트와 중복 방지

각 이벤트는 operationId(UUID), 요청 의미의 digest, goalId/requestId/소유 범위, eventId, revision, source, quantity, native 확인 시각, supersedesEventId, 정정 사유를 가진다. 최초 확인은 이전 이벤트 없음, 정정은 해당 요청의 최신 이벤트를 정확히 지정해야 한다.

- 현재 허용 출처는 `user-confirmed` 하나다. native가 출처를 지정한다. 클라이언트가 `official-verified`를 제출해 승격할 수 없다.
- quantity는 null 또는 0~5,000,000 정수. 사용자 확인 커밋에는 null을 허용하지 않는다. 이 상한은 **제품 입력 안전 한도**이며 실제 게임의 대성공 상한을 확인했다는 뜻이 아니다.
- 빈 문자열·공백·음수·소수·비유한 수·안전 정수/한도 초과는 거절한다. 한도 초과는 입력을 보존하고 보류 안내하며 clamp하지 않는다.
- 예상량보다 많은 수량은 허용하되, 정확한 입력값과 예상량을 다시 보여주는 명시적 재확인을 요구한다. 정정·초과 확인 토큰은 requestId/수량/기준 revision에 묶는다.
- 같은 operationId·같은 의미의 재전달은 이미 커밋한 결과로 응답한다. 같은 operationId·다른 의미는 충돌이다. 버튼 중복·ACK 유실 때문에 수량이 다시 더해지지 않는다.
- 새 operationId라도 같은 요청의 최초 확인을 두 번 만들 수 없다. 다른 값은 명시적 정정 흐름으로만 허용한다.
- 정정 전·후 값과 시각·사유를 보존한다. 예: 요청값3→2는 합계5가 아니라 **해당 요청 기여분2로 교체**다.
- confirmedQuantity는 요청별 최신 유효 확인값을 합산한 파생값이다. 총합을 별도 권위 값으로 저장하지 않으며 정수 오버플로도 차단한다.

합산 대상은 해당 goal의 정확한 목표 품목에 대한 유효한 제작 확인 이벤트뿐이다. 가공 registered·예상 산출·다른 품목의 선행 목표 수량은 합산 대상이 아니다. confirmedQuantity=0이라는 합계와 개별 요청 quantity=null이라는 미확인 상태는 함께 존재할 수 있다.

중복 operationId 확인을 새 revision CAS보다 먼저 수행한다. 이미 반영된 요청이면 원래 커밋 식별 정보와 **현재 저장 revision의 읽기 모델**을 반환한다. 나중에 정정된 뒤 옛 operationId가 재전달돼도 옛 수량으로 화면/파일을 되돌리지 않는다. UI도 범위·generation·revision이 오래된 ACK를 현재 상태에 적용하지 않는다. 이벤트 순서는 revision/연결 체인으로 결정하고 PC 시계나 타임존 변경에 따라 재정렬하지 않는다.

확인량을 낮추면 완료 판정도 취소될 수 있다. 해당 진척을 근거로 만든 재료 계획·예약·계속하기 준비를 무효화한다. 이미 실행한 게임 행동을 되돌렸다고 표시하지 않는다. 후속 실행 중에는 정정 커밋을 차단하고 입력 초안만 보존한다.

### 4.4 초기 저장 한도

v1은 환경별 최대100목표·1,000요청·4,000감사 이벤트·평문 직렬화4MiB 중 먼저 도달한 한도로 제한한다. 80%에서 경고한다. 파일 크기/배열/문자 길이를 복호화 전후 모두 검사한다.

한도 도달 시 기존 목표·정정·중복 방지 tombstone을 자동 삭제하지 않는다. 새 변경을 거절하고 기존 읽기·보류/복구 안내를 제공한다. 별도 승인된 아카이브 설계 전에는 무제한 기록·자동 정리를 구현하지 않는다.

## 5. 원자적 저장·동시성·복구

### 5.1 커밋 순서

1. native가 현재 문서 origin/epoch·환경·계정·캐릭터와 정확한 명령 payload를 확인한다. 브라우저가 파일 경로를 지정할 수 없다.
2. 새 진행 파일 전용 프로세스 간 파일 잠금을 얻는다. revision CAS와 operationId 중복 검사는 이 잠금 안에서 수행한다. 메모리 mutex만으로 다른 IRIS 프로세스를 배제하지 않는다.
3. 현재 파일을 검증해 변경 후보를 만든다. 이벤트·요청·목표 변경·중복 방지 정보가 같은 후보에 들어간다. 기존 실행 원장/자동 저장 파일에는 쓰지 않는다.
4. 환경·스키마별 독립 entropy와 DPAPI CurrentUser로 암호화한다. 같은 디렉터리의 고유 임시 파일에 CreateNew/배타 쓰기 후 Flush(true)한다. 평문 임시 파일은 만들지 않는다.
5. 임시 암호문을 다시 읽어 스키마·범위·합계·정정 체인·revision을 검증한다. 실패하면 현행 파일을 교체하지 않는다.
6. 기존 파일이 있으면 File.Replace로 직전 암호문을 고유 backup으로 보존하며 교체한다. 최초 저장은 File.Move를 쓴다. 파일시스템이 이를 지원하지 않으면 실패로 보고하며 직접 덮어쓰기로 대체하지 않는다.
7. 현행 파일을 다시 검증한 뒤 저장 ACK를 보낸다. ACK가 오기 전 UI는 이전 확인량을 유지한다. 교체 후 ACK만 유실됐으면 같은 operationId의 **로컬 기록 조회/재전달**로 한 번만 반영한다. 게임 confirm 명령을 재전송하는 것이 아니다.

정상 커밋 검증 후에만 해당 저장소가 만든 구세대 백업을 정리해 직전2세대를 유지할 수 있다. 현행 이벤트 이력은 잘라내지 않는다. 장애 잔여물·충돌 분기·미지원 버전·복구 중인 세대는 자동 삭제하지 않는다. 이 정리는 기존 native 원장·그 백업에 적용하지 않는다.

### 5.2 실패와 재시작

- 임시 파일 기록 중 종료: 현행 파일을 권위로 유지. 남은 tmp는 커밋된 진척으로 자동 승격하지 않는다.
- 교체 후 ACK 전 종료: 현행 파일의 operationId·revision을 다시 조회해 중복 없이 복구한다.
- 파일 손상/키 불일치/지원하지 않는 스키마/필수 파일 누락: 기존 파일을 원위치 보존하고 빈 저장소로 덮지 않는다. last-good backup을 **복구 후보**로만 보여준다.
- backup이나 tmp가 있는데 현행 파일이 없으면 ‘처음 사용’으로 취급하지 않는다. 한설의 명시적 복구 선택 전 읽기/검토 모드다.
- 복구는 별도 새 revision과 복구 출처를 남기는 진행 파일 작업이다. 누락된 최신 확인·operationId·제출 요청을 대조하지 못하면 추가 소비/목표 완료를 계속 차단한다. 가장 높은 revision을 골랐다는 이유만으로 자동 허용하지 않는다.
- 모든 파일이 삭제되거나 외부 프로그램이 유효한 옛 암호문 전체를 되돌리는 경우까지 로컬 파일만으로 완벽히 감지한다고 주장하지 않는다. 불명확한 연결은 아래 정합성 규칙으로 막는다.
- DPAPI는 현재 Windows 사용자/PC 중심이다. 다른 PC로 파일을 옮겨 자동 복구하는 기능은 이번 범위 밖이다.

### 5.3 버전 관리와 잠금 순서

schemaVersion과 문서 revision은 다르다. 알려진 구버전의 향후 변환도 원본 백업·변환 후보 검증·원자적 커밋 후에만 허용하며 읽기 중 자동 변환은 하지 않는다. 미래 스키마는 보존 후 읽기 차단한다. 과거 completedOutput 예상 진척을 새 확인량으로 이관하지 않는다.

새 진행 파일 잠금을 잡은 채 native 원장 객체를 새로 생성하거나 게임 실행 lease를 취득하지 않는다. 실행 코디네이터는 기존 mutation/lease/원장 잠금 순서를 유지한다. 원장 snapshot은 기존 관리 객체에서 잠깐 읽고 잠금을 반환한 다음 진행 파일 CAS에 사용한다. 소비 직전에는 기존 실행 코디네이터 안에서 새로 대조한다. 별도 수량 저장 잠금이 게임의 전역 실행 lease를 대체하지 않는다.

## 6. native 원장과의 정합성·실행 전 연결

### 6.1 두 파일을 한 트랜잭션이라고 가정하지 않는다

진행 기록과 실행 원장은 별도 파일이므로 한 번에 원자적으로 저장되지 않는다. 이를 숨기지 않고 다음 순서와 중간 상태를 보존한다.

1. 실행할 목표를 먼저 진행 파일에 저장한다. 실패하면 실행 준비/최종 실행으로 넘어가지 않는다.
2. 기존 prepare가 생성한 nonce와 native 동결 메타데이터를 해당 목표에 연결해 `prepared` 요청을 저장한다. 입력값으로 native 메타데이터를 위조하지 못하게 한다. 저장 후에만 최종 실행 버튼을 활성화한다.
3. 기존 native confirm의 최종 동의·재검증·lease 경계에서 바인딩과 수량/저장/보류 gate를 다시 확인한다. 같은 nonce의 바인딩을 누락한 구 호출로 우회하지 못하게 한다. 새 승인된 목표 경로에서 필수 연결이 없으면 최신 기능 필요로 거절한다.
4. 기존 journal.Begin/UpdateCrafting/게임 실행 순서와 안전 원장의 normal outcome 기록을 그대로 사용한다. 이 설계가 원장 필드나 unknown 정책을 바꾸지 않는다.
5. native 원장에 종료가 기록된 뒤 진행 쪽에 종료 관측을 기록한다. 진행 저장 실패를 이유로 이미 확정된 native outcome을 completed↔unknown으로 바꾸지 않는다. 진행 쪽은 저장/대조 필요 상태로 막는다.
6. `completed`와 정확한 연결을 확인한 제작 요청만 사용자 수량 확인 대상으로 삼는다. 정상 종료라도 실제 수량은 null이며 사용자 확인 전에는 0으로 만들지 않는다.

진행 쪽 prepared/제출 가능 상태와 원장 없음 사이에서 앱이 종료되면, 요청을 보내지 않았다고 단정하지 않는다. 현재 세션에서 native 취소 ACK·실행 전 취소임을 확정할 수 있는 경우만 취소 이벤트를 기록한다. 재시작 후 제출 여부가 애매하면 `제출 여부 확인 필요`로 보존한다. 기존 nonce를 재생하거나 새 요청을 자동 발행하지 않는다.

### 6.2 대조 표

| native 원장 | 진행 기록 | 처리 |
| --- | --- | --- |
| 정확히 같은 요청·완료·동일 소유자/품목/메타데이터 | 수량 미확인 | 사용자 확인 가능. 추가 제작 차단 |
| 정확히 같은 요청·완료 | 사용자 확인 수량 저장됨 | 사용자 확인 진척으로 표시. 모든 다른 gate가 통과한 경우에만 수량 목표 달성 판단 |
| inflight 또는 unknown | 어떤 수량/상태든 | 실행 보호 유지. 신규 수량 반영/정정·완료·계속하기 차단. 이미 저장된 과거 확인 이력은 삭제하지 않음 |
| 다른 캐릭터/계정/품목/횟수 또는 상반된 종료 상태 | 연결 존재 | 충돌/검토 필요. native를 진행 기록에 맞춰 고치지 않음 |
| 해당 요청 기록 없음 | prepared/제출·종료·확인 기록 존재 | 대조 불가. 완료·추가 소비 차단. 오래돼 정리됐을 수 있어도 성공으로 보충하지 않음 |
| 신규 목표 연결 없이 과거 완료 원장만 있음 | 신규 진척 없음 | 과거 예상량/확보량을 가져오지 않음. 기존 unknown 전역 보호는 별도로 유지 |

현재 native 원장의 30일/300건 정리를 바꾸지 않는 대가로, 대조 원장이 사라진 **활성 목표의 자동 재개는 불가**다. 당시 확인 이력은 ‘과거 사용자 확인 기록’으로 읽을 수 있지만 현재 목표 완료/추가 실행 허가로 승격하지 않는다. 다음 절의 보완은 **역사적 증거를 잃지 않기 위한 보존 정책**이며 이 기본 차단을 완화하지 않는다.

원장 snapshot과 UI 표시 사이의 경쟁은 실행 직전 native 재검증으로 막는다. 진행 파일에 `실행 가능=true`를 영속 저장하지 않는다. 다른 목표/계정/환경의 기존 unresolved·lease 차단도 계속 적용한다. 격리·분리된 과거 unknown 기록도 수량이 증명된 completed로 취급하지 않는다.

### 6.3 장기 보존 대안과 권장 정책 — 후속 검토안

| 대안 | 장점 | 제한·위험 | 제안 |
| --- | --- | --- | --- |
| A. 기존 원장 불변 + 최소 종료 증거 별도 저장 | 원장 정리 후에도 당시 연결/확인 출처를 설명할 수 있음. 실행 보호와 분리 | 종료 증거를 저장하기 전에 중단되면 사후 복원이 안 될 수 있음. 증거는 실행권한/실수량 아님 | 채택 후보 |
| B. 진행 중 목표의 필수 기록만 제한적으로 유지 | 활성·보류 목표의 요청/정정/최소 증거를 보존하고 기록 상한을 통제 | 상한에 도달하면 새 요청/변경을 멈춰야 함. native 원장 자체를 pin하면 기존 정리/안전 정책 변경이 됨 | **A와 결합하되 새 진행 파일 안에서만 보존** |
| C. 원장 정리 후 사용자 확인으로 복구 | 사용자가 기억/게임 화면으로 수량 이력을 보완할 수 있음 | 사용자 진술로 과거 명령 종료·nonce·소유자·비용·unknown 해결을 증명할 수 없음 | 수량 보완 기록만 가능. 실행 안전 복구 수단으로 사용 금지 |

권장안은 **A+B의 유한한 sidecar 보존**이다. 원장 pinning·정리 조건 변경·과거 원장 복원/재작성은 제외한다. 목표/요청/정정 이력은 기존 v1의 100목표·1,000요청·4,000이벤트·4MiB 한도를 유지하며, 종료 증거도 같은 문서/한도 안에서 요청별 최대1개를 보존한다. 반복 폴링마다 복사하지 않는다.

최소 종료 증거는 native가 **당시 존재하는 정확한 원장 행**을 읽어 대조한 뒤 생성한다. 필드는 environment/goalId/requestId/accountId/characterId/action/정확한 품목, 동결된 제작 메타데이터(있는 경우), 원장 terminal outcome·startedAt·관측 시각·검증기 버전·그 행의 canonical digest다. 원문 CLI 응답·보상 배열·계정 토큰·UI 제출 결과·‘실행 가능’ 값은 보존하지 않는다. SHA digest나 DPAPI가 서버 서명/악의적 롤백 방지를 보장한다고 주장하지 않는다.

- 제작 completed와 가공 registered는 각자의 종료 사실만 증언한다. `registered`는 수령/생산 완료가 아니며, completed도 실제 확보 수량이 아니다.
- inflight/unknown은 종료 증거로 발급하지 않는다. unknown을 분리했다는 감사 기록도 completed 증거로 바꾸지 않는다.
- 기존 증거와 다른 terminal 증거가 재도착하면 교체하지 않고 충돌/검토 필요로 막는다. 없는 원장 행을 UI나 사용자 확인으로 지어내지 않는다.
- 활성·보류 목표의 필수 요청/확인/정정/증거는 자동 정리하지 않는다. 취소·삭제·완료 후에도 기록은 유지한다. 한도 도달 시 기록을 버려 자리를 만드는 대신 새 요청/기록 변경을 거절한다. 별도 내보내기/아카이브/파기는 이번 계획 밖이다.
- 80% 경고·용량 사전 점검 후 실행 전 바인딩을 저장한다. 종료 기록은 바인딩된 요청의 고정 슬롯을 사용하고, 실행 중 새 무관 이벤트로 그 슬롯을 소진하지 못하게 한다. 예산 산정이 실패하거나 한도를 넘으면 실행 전 차단한다. 디스크 장애까지 저장 성공을 보장하는 것은 아니므로 종료 저장 실패 시 기본 보호/복구 규칙은 유지한다.

**원장이 정리된 뒤 할 수 있는 것:** 기존 증거/사용자 확인 이력 읽기, 원래 목표·보류 상태 복원. 사용자의 수량 보완·정정을 `검토 대기 진술`로 별도 보존하는 복구 대안은 검토할 수 있지만, 이 진술을 유효 진척 합계나 완료 판정에 적용하면 안 된다. 별도 진술 저장 UX는 현재3단계 구현 범위에서 제외하며 후속 승인을 받는다.

**할 수 없는 것:** 과거 native 종료를 새로 확정, 요청/캐릭터 귀속 재배정, unknown/lease 해제, 확인된 비용 추정, 현행 목표 완료 승격, 과거 요청 재실행 또는 자동 계속하기. 유효 증거가 남아도 현재 원장이 없으면 기본 N08 차단을 유지한다. ‘과거 확인량’과 ‘현재 재개 가능’은 UI에서도 분리한다.

이미 정상 저장한 과거 사용자 확인량/최소 증거는 원장 누락 때문에 삭제하지 않는다. 다만 현재 목표의 완료/추가 소비는 검토 상태로 유지한다. 이 제약을 완화하는 새로운 실행권한 복구 정책은 별도 검토·승인이 필요하다.

이 보완의 저장 형식/한도·후보 증거 객체는 1차 저장 기반에서 합성 자료로 검증하고, 실제 native 대조·발급은 2차에만 연결한다. 게임 실행기나 UI가 없는 1차 저장 구현이 종료 증거를 실제로 검증했다고 보고하면 안 된다.

## 7. 사용자 확인·보류·취소 UX

### 제작 결과 확인

제목 `ERGON · 제작 결과 확인`. 품목·원래 목표·선택 캐릭터, 이번 제작 횟수, 참고 예상량을 표시한다. 기본 안내: ‘제작 명령이 종료됐어요. **이번 제작으로 추가 확보한 개수**를 확인해 주세요.’ 입력 기본값은 빈칸이며 가방 총보유량이 아님을 짧게 표시한다.

- 결과 확인: 유효 숫자를 입력하고 필요한 초과/정정 확인까지 마친 뒤 로컬 저장. 저장 중 중복 누름 차단. ACK 후 ‘사용자 확인 3개 · 목표4 · 남은1’처럼 표시한다.
- 0 입력: 명시적 ‘0개로 확인’을 한 번 더 확인. 빈칸/닫기는 미확인으로 유지한다.
- 나중에 확인: 목표 보류를 저장하고 확인 화면을 닫는다. 저장 실패 시 ‘보류가 저장되지 않았어요’와 입력을 유지하며 실패를 숨기지 않는다. 화면 닫기/Escape 자체는 0개 확인·소비 동의가 아니다.
- 높은 수량: ‘예상보다 많아요. 이번 요청으로 확보한 수량이 맞나요?’로 값 자체를 재확인. 예상량으로 잘라 저장하지 않는다.
- 정정: 이전 값·새 값·사유를 보여주고 새 이벤트로 저장. 현재 선택 캐릭터가 달라지면 이전 입력을 다른 캐릭터 화면에 재사용하지 않는다.

입력 중 캐릭터/메뉴 이동·앱 닫기에는 기존 자동 저장 상태와 별개의 미저장 결과 확인 경고를 제공한다. ‘버리기’는 입력 초안만 버리며 미확인 요청·원장·저장 이력을 지우지 않는다. 입력 초안을 별도 평문 디스크에 자동 저장하지 않는다.

### 남은 목표와 버튼 범위

- 목표 미달: 확인량을 유지하고 남은 수량 계산. 미확인/충돌/저장 실패가 하나라도 있으면 ‘남은 수량 확인 필요’가 우선이다.
- 목표 달성: 확인량이 목표 이상이고 미해결 요청·원장 충돌·복구 문제가 없을 때만 완료. 초과분을 표시할 수 있지만 실제 가방 재고로 더하지 않는다.
- 계속하기: 향후 구현 가능 범위는 기존 재고/예약 조회와 부족분 미리보기 재계산, 직접 준비 단계까지다. 클릭으로 game confirm을 호출하지 않는다. 이번 설계 작성 단계에는 버튼을 추가하지 않는다. 다음 구현에서도 연결/검증되지 않은 재계획 기능은 동작 버튼처럼 노출하지 않는다.
- 보류하기: lifecycle=paused 저장, 진척·요청·이력 유지. 진행 중 게임 행동을 강제 중지하지 않는다.
- 그만하기: lifecycle=cancelled 저장, 목록에서 활성 목표만 숨김. 이미 요청한 행동은 계속 관측하고 결과 확인 기록을 남길 수 있지만 목표 완료/자동 재개는 하지 않는다.

취소/보류와 수량 상태는 별도이므로 수량을 확인해도 보류/취소가 자동 해제되지 않는다. 재시작 후도 자동 실행하지 않는다.

## 8. 계획 삭제·자동 저장·캐릭터 전환 충돌 방어

### 계획 삭제는 기록 삭제가 아니다

현재 계획의 localStorage와 새 native 진행 기록 사이도 한 파일 트랜잭션이 아니다. 삭제 시 native 목표의 비활성화/tombstone 저장 ACK를 먼저 얻고, 그 뒤 기존 계획 초안에서 제거한다. 두 번째 단계가 실패하면 취소된 목표의 계획 카드가 남을 수 있으나 실행은 차단하고 재삭제 안내를 제공한다. native 단계 실패 시 정상 삭제 완료로 안내하지 않는다.

외부 편집 등으로 계획만 사라져도 진행 기록은 ‘목록에서 빠진 목표’로 보존하고 자동 활성화/삭제하지 않는다. 연결된 선행 목표와 요청도 보존한다. 동일 품목을 새로 추가해도 새 goalId이며 이전 확인량을 자동 이전하지 않는다. 실행 중 삭제도 게임/unknown 원장·감사 자료를 삭제하거나 안전 잠금을 해제하지 않는다.

기존 계획 목록은 계정 공용이지만 진척은 캐릭터별이다. 현재 캐릭터의 목표 비활성화/계획 제거가 다른 캐릭터 목표까지 취소할 권한은 아니다. 다른 캐릭터의 기록은 변경하지 않고, 다음 조회 때 원래 계획이 없으면 분리 보존된 목표로 안내한다. 현재 캐릭터의 확인량을 계정 공용 계획 카드에 섞어 저장하지 않는다.

### 기존 자동 저장과 분리

- `pending-v3`/15초 자동 저장/서버 요청ID/dirty 보호에 ERGON 확인 이벤트를 넣지 않는다. 기존 저장 버튼·변경 버리기가 ERGON 기록을 지우지 않는다.
- ERGON 확인 커밋은 즉시 native 로컬 저장 ACK를 기다린다. 서버 저장 성공 알림을 ERGON 저장 성공으로 재사용하지 않는다.
- 기존 `onActionBusyChange` 등 게임 busy와 새 `progressSaving` 상태를 구분한다. 저장 중 중복 확인·새 게임 준비는 막되 작업 기록 읽기까지 무한 busy로 묶지 않는다.
- 새 기록 로드/수량 확인/보류에는 CLI를 붙이지 않는다. 기존 생활 폴링을 늘리거나 숨은 창에서 새 폴링을 시작하지 않는다.
- 계정·캐릭터 전환 전 진행 저장 중이면 완료/실패를 명확히 처리한다. 늦은 응답은 원래 범위 저장 결과로만 남고 현재 화면의 진척을 갱신하지 않는다.
- 복원은 전체 scope를 대조한 후 이루어지며 기존 계정별 공용 계획 초안을 캐릭터별 확정 진척으로 오인하지 않는다.
- 종료 조정자는 기존 미저장 숙제 경고와 새 ERGON 경고를 함께 보되, 어느 한쪽의 저장/버리기를 다른 쪽의 성공으로 간주하지 않는다. 강제 종료 시 미저장 입력 소실 가능성을 숨기지 않는다.

## 9. native/프런트엔드 경계와 영향 파일 후보

아래는 **후속 구현 후보**이지 현재 존재하는 API가 아니다.

- native 전용 진행 저장 서비스: 별도 스키마/범위 검증, 로드/CAS 이벤트 커밋, 요청 연결, 읽기 전용 원장 대조. 생성자에서 실제 원장을 복구/수정하지 않는다.
- bridge: 기존 인증 문서 origin/epoch와 공개 ERGON gate를 유지하는 명시적 allowlist. 파일 경로·임의 전체 스냅샷·임의 source/native outcome을 받지 않는다. native가 시각과 출처를 지정한다.
- 프런트엔드: strict DTO parser, 마지막 ACK 읽기 모델, 미저장 입력 UI. localStorage 진척 fallback 없음. 구 native에 새 저장 계약이 없으면 확인 저장 기능을 비활성화하고 최신 앱 필요를 안내한다.
- 실행 연결: 기존 executor/최종 확인 경계에 요청 바인딩 저장/대조 gate만 추가 검토. 기존 안전 원장 형식/SetOutcome/nonce·lease 의미는 변경하지 않는다.
- 후보 파일: 새 `iris/desktop-life-progress.cs`, 새 진행 도메인·parser/hook, `iris/desktop-bridge.cs`, `iris/desktop-webview.cs`, `lib/irisDesktopStore.ts`, `lib/irisErgonCraftGoal.ts`, `DesktopErgonExecution/Queue/PlanRow.tsx`, `DesktopErgon.tsx`, 종료/미저장 보호 연결, native 소스 컴파일 목록과 관련 fixtures. 이 문서는 해당 파일을 생성/수정하지 않았다.

공식 보상 어댑터는 향후 **native 검증 증거 → 동일 requestId의 확인 이벤트** 경계로 들어온다. 보상 파서·추정 합산·‘빈 배열=0’ 규칙은 없다. 공식 증거와 기존 사용자 확인이 같은 요청에 있으면 둘을 더하지 않고 검토 가능한 대체/정정 이력으로 연결해야 한다.

## 10. 무료 운영·보안

진행/확인/정정/복구의 신규 Supabase DB/API·Realtime·Storage 호출, Vercel 함수·예약 실행·파일 업로드는 **0**이다. 상세 데이터는 native 로컬에만 남는다. 기존 계획/생활 조회와 서버 자동 저장의 기존 호출량을 늘리는 설계가 아니다.

실제 ID·계정·캐릭터·품목별 원문 응답·토큰·개인 경로·암호문/백업을 Git이나 채팅에 복사하지 않는다. 진단은 버전·오류 분류·익명화한 합성 ID만 사용한다. 실제 데이터 내보내기/다른 PC 동기화/원격 실행은 별도 설계·승인 과제다.

## 11. 검증과 다음 승인

실행할 합성 시나리오와 통과 조건은 [검증 계획](../../ERGON_PROGRESS_SYNTHETIC_VALIDATION_PLAN_20261021.md)에 분리했다. 이번 설계 단계에서 새 시험 코드나 제품 회귀를 실행하지 않았으며, 모든 계획 항목은 **미실행**이다.

설계 자체의 수용 조건: 위8개 사용자 조건, 원장 정리/두 파일 중단 창/ACK 유실/삭제 실패 순서가 문서에 빠짐없이 대응하고, 예상량을 확인량으로 승격하는 경로와 저장 실패 후 성공 안내 경로가 없어야 한다.

기본 방향의 한설·뉴월 승인을 반영해 [3단계 구현 계획](../plans/2026-10-21-ergon-progress-three-stage-implementation.md)을 작성했다. 장기 보존 보완/계획의 검토와 **1차 구현 시작 승인**은 별도다. 실제 게임·운영·공개 잠금·commit/push·배포 승인은 포함하지 않는다. 우선 위험은 **실행 전 요청 바인딩, 원장 대조 누락, 커밋 ACK 유실 중복, 종료/캐릭터 전환 중 저장**이며, 전체 자동 생산 엔진은 다음 단계로 유지한다.
