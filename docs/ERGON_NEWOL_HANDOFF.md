무료 제약은 Supabase Free/Vercel Hobby 추가 구독 없음이다. 상세 진행·원장은 PC 로컬, 서버 최소 요청/결과만 검토한다. 설계에20~40명 가정별 쓰기/폴링/전송량을 산정했으며 실제 기존 사용량·Hobby 개인/비상업 조건이 미확인이면 원격을 보류하고 로컬 대안을 유지한다. 이번에는 서버 요청·DB·Realtime·Storage를 추가하지 않는다.

증거 수준은 다음처럼 읽는다.

| 표기 | 뜻 |
| --- | --- |
| 코드 확인 | 기준 소스에 실제 경로가 있음. 공개 사용·실게임 성공과 별개 |
| 합성 검증 | 가짜 CLI/bridge/재고 또는 실제 React 컴포넌트 시험. 게임 실행 아님 |
| 과거 실측·사용자 확인 | 당시 한정된 행동의 기록. 다른 품목·캐릭터·현재 버전까지 일반화 금지 |
| 제안·미확인 | 목표 또는 설계 후보. 구현 완료·실행 승인으로 해석 금지 |

**요약:** 조회·계획 편집·부족분 미리보기·제한된 단일 실행·보호 원장은 있다. 그러나 **부족 재료 채집부터 가공·수령·재등록까지 목표 수량을 끝까지 만드는 자동 생산은 아직 없다.**

## A. 최종 사용자 목표

### 한설이 최신 대화에서 명확히 한 동작

“목재를 추가100개 만들어 둬”라는 한 번의 명령에 대해 다음을 연결한다. 가공 등록 한 번이나 작업 목록에 넣는 것만으로 완료하면 안 된다.

1. 시작 시 목재 보유량과 사용 가능한 통나무 등 재료를 확인한다.
2. 추가 생산100개에 필요한 **부족 재료만** 계산하고 통나무를 채집한다.
3. 가공 시설로 이동해 필요한 만큼 작업을 나누어 등록한다.
4. 시설이 차면 기다리고, 완료품을 수령해 빈자리를 만든다.
5. 남은 생산량을 재등록하며 실제 추가 생산·수령 목표를 충족하면 종료한다.

`재고·부족분 확인 → 선행 채집/가공 → 완료품 수령 → 후속 가공/제작 → 목표 확인`

- 시작 가방 목재30개에 추가100개라면 기준 목표는130개다. 기존 완제품30개를 추가 생산100개에서 빼지 않는다. 기존 원재료는 중복 채집하지 않는다.
- 추가 생산량·최종 보유 목표·등록 횟수·가공 중 예상 산출·실수령량은 별도 값이다. 등록·예상 산출을 가방 재고로 사용하지 않는다.
- 단위 산출 때문에 초과 생산할 수 있다. 예를 들어 산출3개라면100개에34회/기본 예상102개가 필요하다. 치명 산출·수동 이동/소비가 있으면 관측은 더 복잡해지므로 정확히100개를 보증하지 않는다.
- 다른 가공품 및 최종 제작에도 같은 개념을 적용한다. 재료표·해금·도구·시설·비용이 확인된 경로부터 지원하며 모든 품목 지원을 미리 약속하지 않는다.
- 여러 목표를 편집하고 공통 재료를 예약하되, 한 번에 한 게임 행동만 실행한다. 다른 목표와 같은 재료를 이중 사용하지 않는다.
- 진행은 `재료 확보 / 등록 / 가공 중 / 수령 대기 / 목표 확인`으로 짧게 보여준다. 중지하면 새 행동을 보내지 않고, 이미 보낸 행동의 결과 관측·기록은 유지한다. 모르면 `확인 필요`이며 완료가 아니다.

기존 문서의 “단일 가공부터”는 개발 순서를 나눈 제안일 뿐 최종 요구를 축소한 결정이 아니다. **첫 완성 사례도 목재의 부족 통나무 채집부터 추가 목표량 생산까지 연결돼야 한다.** 이번 문서는 이 요구를 기록하며 자동 소비 정책·구체 구현 명세의 승인을 대신하지 않는다.

### 생산·시설·비용

- UI의 목표100개가 현재 native 가공 intent까지 전달되지 않는다. 횟수 계산만 고쳐도 실제 자동 생산은 완성되지 않는다.
- 실제 시설 작업/완료/잔여 시간은 읽지만 **총정원·안정적인 작업 ID는 현재 정규화 모델에 없다.** 같은 이름·시설의 작업 수 차이는 보조 증거이지 자기 작업의 완전한 귀속이 아니다. 다른 앱·수동 등록/수령이 끼면 확인 필요로 멈춰야 한다.
- 등록 예산과 총예산을 분리한다. 산출3개의 추가100개는34회/기본102개, 회당5 계약이면 **등록분170날개**다. 채집·수령·원격 전송 비용까지 전부 포함한 금액이 아니다. 과거 수령 날개 변화 없음도 모든 품목 무료의 증거가 아니다.
- 창고 재료는 무조건 불가도, 무조건 가방과 합산도 아니다. **마이홈 재료 전송기·연금술 부스러기·주간 확인창** 조건이 있다. 현재 설치·품목별 비용·임의 모달 승인 지원은 미확인. 자동 확인/일주일 숨김 승인 없음.
- 일부 참고 재료를 읽는 `iris/desktop-life-reference.cs`는 선택 품목의 제한된 사실만 반환하고 complete:false로 표시한다. 외부 설치 자료 의존과 재사용 권리는 남은 문제다. 외부 캐시 Owned를 현재 재고로 쓰거나 전체 DB를 배포하지 않는다. 독립적으로 허용된 재료표를 확보해야 한다.

### 실패·기록·복구

- native는 승인 전에 재조회·nonce/컨텍스트 확인·실행 lease·원장 선기록을 사용하고, 실행 후 응답/작업 변화/비용을 결합한다. accepted·exit0·등록만으로 최종 목표 완료를 선언하지 않는다.
- timeout/응답 유실·앱 재시작의 inflight는 unknown으로 보존한다. 자동 재전송·강제 성공 주입·원장 삭제로 잠금을 풀지 않는다.
- 현재 원클릭 수령 복구는 조건이 충족된 과거 unknown의 **실행 종료 확인을 별도 감사 자료로 분리**하는 제한 경로다. 원본 성공 판정이나 모든 행동의 포괄 재개 허가가 아니다. 새로 불명확해진 현재 실행과 분리한다.
- 특정 과거 제작의 unknown 기록이 보존 중이다. 이 공개 문서에는 실제 계정/캐릭터/원장 ID·원문·위치를 싣지 않는다. 원본 확인은 해당 PC의 승인된 진단 흐름으로만 수행한다.

### 한설/뉴월이 판단할 핵심 질문

1. **시작 승인 범위:** 지금처럼 명령마다 확인할지, 제한된 목표·횟수·총소모·시설 수령 범위를 한 번 승인할지. 한 번 승인하는 방식은 최종 UX의 권장안이지만 구체 정책은 아직 구현/승인되지 않았다. 사용자 지정 실행시간은 요구하지 않으며 안전용 timeout/무진척 제한은 별도다.
2. **목표의 예외:** 묶음·치명 초과 산출 허용 표시, 진행 중 사용자가 물품을 소비/이동했을 때 일시정지할지. 목표를 조용히 늘리거나 남의 생산을 내 진척으로 세지 않는 방향을 권장한다.
3. **원격 재료:** 기본 가방만 사용할지, 전송기·부스러기 예산을 확인한 뒤 창고 사용을 허용할지. 주간 확인창은 사용자가 직접 처리하는 단계가 우선이다.
4. **출시 기준:** 먼저 검증된 목재 같은 제한된 경로부터 공개할지, 여러 품목까지 기다릴지. “모든 품목” 요구와 지원 계약이 확인된 첫 범위를 구분한다.

## G. 뉴월 협업 운영과 자료 지도

뉴월은 이 문서로 “목표/현재/증거/미확인/결정”을 판단한다. 영겁·순월의 상세 시간순 이력·수신 ACK·금지사항은 기존 **CODEX_RELAY/HANDOFF 체계를 유지**한다. 이 문서가 릴레이 수신 확인을 대신하거나 과거 누적을 삭제하지 않는다.

중요 기능 완료, 개발 방향 변경, 새 문제 발견, 검증 수준 변경 때 기준 날짜·코드 SHA와 함께 해당 항목을 갱신한다. 상태가 다르면 최신 코드/실측과 원인을 대조하고 과거 문서 문장을 최신 사실로 복사하지 않는다. 새 기능을 뉴월에게 설명할 때도 코드 확인·합성·실측·공개 가능을 따로 보고한다.
