# ERGON — 한설 요구사항과 다음 작업대 제안 (2026-10-16 KST)

상태: 사용자 요구사항 인계 + 순월의 화면 재설계 제안. **새 작업대 설계/구현 승인 완료 문서가 아니다.** 현재 화면의 작은 오류 수정과 구분한다. 집에서 이 문서부터 다시 확인하며 같은 요구를 사용자에게 처음부터 설명하게 하지 않는다.

## 사용자가 원하는 결과

생활 커넥터처럼 현재 캐릭터·품목·재료·작업을 한눈에 보고, 만들 품목을 담고 수량을 수정한 뒤 시작하는 생활 작업대. 예: 크로노스 물물교환/임무에서 필요한 상급 목재4개 중 실제 보유3개라면 부족1개만 추가 생산. 부족 재료는 채집→가공→완료품 수령→최종 제작까지 이어지고, 현재처럼 1개만 만든 뒤 멈추거나 수동 준비 화면을 계속 왕복하지 않아야 한다.

## 명시된 불편과 요구

- 작업 선택 드롭다운이 불편하다. 계획 목록에서 바로 선택·수량 수정·삭제·품목 변경을 할 수 있어야 한다.
- 즐겨찾기로 자주 쓰는 품목을 빨리 찾고 계획에 넣고 싶다.
- 현재 재료·재화·시설 작업의 실시간 피드백과 한 화면에서 대부분의 조작이 필요하다.
- 보호/기록/준비 안내가 본문을 길게 차지하고, 사용자가 여러 단계의 확인을 반복하는 현재 동선은 불편하다. 보호 자체 삭제 요청과 혼동하지 않는다.
- 기존 `DesktopErgonQueue`에는 접힌 전체 대기열 안에 수량 수정/선택/제거가 이미 있다. 기능을 새로 복제하기보다 **기본 작업 목록에 노출**해야 한다. 품목 교체·즐겨찾기는 현재 미구현이며 추가 설계 대상이다.

## 이전 요청까지 포함한 기능 범위

1. 크로노스 물물교환/임무게시판 카드 → 제작 대기열 담기. 담을 때 또는 작업 목록에서 수량 지정. 장바구니처럼 여러 품목을 편집한 뒤 시작.
2. 추가 생산 수량과 총 보유 목표를 구분. 기존 확인된 결과·등록 중 생산·실제 재고를 중복 계산하지 않고 부족분만 수급. 가공품이 만들어지기 전에는 보유 재료로 쓰지 않는다.
3. 선행 재료의 채집/가공/제작을 연결. 시설별 실제 슬롯 수·완료시간을 반영하고 목표20개라면 빈 슬롯에 나누어 등록. 사용자 예시: 7슬롯 중4개 완료 → 전체 수령 → 빈4슬롯을 필요한 만큼 재등록. 최소/최대 슬롯을 코드에서 추측하지 말고 공식 근거 확인.
4. 시작 옆에 현재 날개/예상 필요 날개, 원격 재료 사용의 연금술 부스러기 비용을 구분 표시. 전체 비용을 모르면 숫자를 지어내거나 무료로 표시하지 않는다. 시작 승인 예산·품목·횟수·중지 범위를 먼저 정한다.
5. 진행 중 현재 단계/생산 진척/남은 수량/시설 타이머/다음 행동을 간단히 표시. 중지·실패 시 이유와 이어갈 동선을 하나로 제공하고 자동 중복 실행을 막는다.
6. PC 완료 알림은 후속 요구에 포함. 모바일 앱·외부 PC연동/푸시는 사용자가 나중에 생각하기로 했으며 이번 PC 작업의 필수 구현으로 확대하지 않는다.

## 창고 원격 재료 사용 — 반드시 보존할 사용자 설명

- 가방에 없더라도 계정/캐릭터 보관함 재료를 게임이 원격으로 사용 가능하다. 인출 명령이 없다는 이유로 사용할 수 없다고 설명하면 안 된다.
- **마이홈에 재료 전송기가 설치되어 있어야 한다.** 다른 캐릭터/계정의 설치 여부를 추측하지 않는다.
- **연금술 부스러기가 소모된다.** 사용자 사진의 목재+ 예시는 비용4이며 모든 품목/수량에 고정4라고 일반화하지 않는다.
- 일주일에 한 번 다시 표시되는 `재료를 전송하시겠습니까?` 확인창이 있고 비용/확인/취소/일주일 동안 보지 않기 항목이 보인다. 사용자는 가능하면 이 확인도 처리하길 원한다.
- 현재 공식 CLI 명령 목록에는 창고 인출이나 임의 모달 확인 명령이 없다. 정식 게임 명령의 blocked/kind와 실제 UI를 대조하고 지원 경로를 확인한다. 주간창이 떠도 성공으로 처리하거나 무한 재시도하지 않는다.
- 비용 확인창 자동 승인 정책은 아직 구현/승인되지 않았다. 비용·품목·범위를 정한 동의 없이 임의로 확인/일주일 숨김을 누르지 않는다. 설치/비용/설정 API가 확인되지 않았으므로 현 단계는 가방/창고를 나누고 원격 사용 조건을 표시한다.

## 2026-10-16 실제 확인 결과 (합성 시험과 구분)

- 한설이 실행 직전 별도 질문→승인→실행 후 결과 질문 방식을 요청. 다음 모든 직접 게임 시험도 이 순서를 따른다. 이번 승인은 목재 시설 수령1회뿐이며 다음 채집/가공/다른 시설 수령 승인으로 재사용하지 않는다.
- 공식 `complete_altering_work`에 상급 목재를 UTF-8/base64 JSON으로1회 전달. 한설이 이동 시작과 실제 수령을 모두 확인했다. CLI exit0/collected7, rewards21개+criticalRewards5개 응답. 전체 완료15→8/목재 작업7→0, 센마이 평원→이멘마하, 날개96,790→96,790. 다른 재화의 보편적인 무료 정책까지 증명한 것은 아니다.
- 실제 수령 CLI는 `status/body` 포장 없이 `collected/rewards/criticalRewards/message`를 직접 반환했다. 기존 native 가정과 불일치하여 성공을 unknown으로 만들 수 있었다. 새 collect 전용 판정은 실제 응답·시설 감소·품목/수량을 함께 확인하며 다른 행동까지 성공으로 추정하지 않는다.
- 아이리스의 동일 readonly 사전점검 경로는 게임 프로세스의 `HasExited/StartTime`에서 Windows 접근거부5 재현. 최소 QUERY_LIMITED_INFORMATION + GetProcessTimes의 생성/종료 메타데이터 확인으로 수정 후 readonly ready 확인. PID/시작시각 대조 유지, 게임 메모리/파일·디버그권한·관리자 권한 추가 없음.
- 공식 재료 조회에서 나무 진액 계정창고40/잠김false, 상급 목재 Alterabletrue 확인. 이후 사용자 사진으로 전송기/부스러기/주간창 조건을 알게 되어 창고를 무조건 가용 재고로 합치려던 접근을 철회했다.
- 직접 CLI 시험은 앱 외부에서 승인받아 수행한 진단이다. 이를 앱의 보호 원장에 성공으로 써넣거나 과거 라이트 크로스보우S unknown을 해제하는 근거로 쓰지 않는다.

## 순월의 권장 화면 (제안 / 사용자 승인 전)

추천은 **목록 중심 단일 작업대**다. 기존 화면에 버튼만 더 붙이는 방식은 왕복/숨은 조작이 남고, 단계별 마법사만 두는 방식은 여러 품목 관리가 어렵다.

- 상단: 현재 캐릭터 / 날개 / 가방 무게 / 부스러기·원격 조건 / 완료품 요약. 상세 기록은 접되 문제 원인/해결 버튼만 짧게 남긴다.
- 품목 영역: 채집·가공·제작 분류, 검색, 즐겨찾기. 품목의 가능/재료 확인/대기 상태와 담기. 즐겨찾기는 로그인 계정·환경별로 보존하고 전체 게임 목록을 복사해 저장하지 않는다.
- **작업 목록을 기본 노출**: 각 행에 품목·추가 목표수량 입력·증감·편집/제거·선택 상태. 드롭다운 제거. 기존 계획/진척 데이터를 재사용하며 선택한 목표와 임시 선행 작업을 구분한다.
- 선택 작업 영역: 필요한 재료 표에 필요/가방/계정창고/캐릭터창고/실제 부족분, 원격 사용 시 설치·소모 조건. 시작 옆에 날개/부스러기 예산과 실제 확인 가능 범위.
- 진행 영역: `재료 확보 → 가공 대기/수령 → 제작 → 완료` 현재 단계와 다음 버튼 하나. 오래된 unknown을 성공으로 숨기지 않고 별도 짧은 보호 배지+복구 동선을 제공한다.
- 넓은 창은 품목/작업 목록/상세 진행3영역, 좁은 창은 작업 목록 중심으로 선택 상세만 펼친다. 320/390px 및18/20/22px 글자에서 버튼/긴 품목명·수치가 잘리지 않아야 한다.

## 집에서 이어갈 우선순위

1. 최신 기능브랜치 pull/개인변경 보존/릴레이 ACK. REA는 집6.5.0 연결 확인 기록이 있으므로 재설치 반복 금지. 실행 중 앱을 강제 종료하지 않는다.
2. 아래 로컬 후보의 정상 재시작 적용 후 사용자 승인 아래 **한 번의 실제 앱 시설 수령**으로 native 차단/결과 판정을 확인. 직접 CLI 성공과 앱 성공은 다르다. 현재 native6428은 후속 프로세스 메타데이터/flat응답 수정 전 실행이다.
3. 창고 조건 표시와 실제 게임 가공 가능 여부를 대조. 다음 가공 시험은 품목/1회 산출/날개5/원격 부스러기 비용 범위를 사용자에게 먼저 묻고 승인 후1회. 주간창은 사용자 직접 확인 또는 별도 승인된 지원 경로만 사용.
4. 한설에게 위 목록 중심 화면 방향을 짧게 확인한 뒤 서면 설계/실행계획으로 진행. 기존 queue 편집/저장/목표 진척을 중복 구현하지 않는다. 사용자가 지금 요구한 것은 더 나은 아이디어와 인계이며 새 큰 재설계의 승인을 받은 것으로 쓰지 않는다.
5. 공식 전체BOM/시설정원/총소비 계약을 확보한 뒤 bounded 생산 엔진과 자동 수령·재충전을 단계적으로 구현. partial 참고표를 완전한 게임 계약으로 승격하거나 다른 프로그램을 무조건 복사하지 않는다.

5시간 잔여15%에서 새 구현 중단→검증/필수문서→정상 기능브랜치 push/인계. 운영 main/공개버전·ZIP/공지/DB 변경은 별도 승인 전 유지한다. 정확 SHA/전송 여부/검증 결과는 최신 HANDOFF와 TO_YEONGGEOP를 따른다.
